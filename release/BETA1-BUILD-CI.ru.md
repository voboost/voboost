# Сборка beta1 через GitHub Actions

Workflow `.github/workflows/beta1-build.yml` собирает новую машинную версию из исходников и выдаёт три артефакта: универсальный macOS DMG, переносимый Windows EXE и Linux x86-64 tar.bz2 с CLI. Он не публикует GitHub Release и не запускает эмулятор. Проверки на машине выполняются отдельно; сборка не объявляет их пройденными.

## Перед коммитом

Сначала подготовьте и закоммитьте компоненты, логотип и codestyle. Архивный репозиторий лицензии не является входом сборки; его прежний pin остаётся историческими метаданными. Затем из корня репозитория продукта выполните:

```sh
node tools/release/prepare-source-pins.ts /absolute/path/to/workspace --write
```

Команда обновляет `release/version.toml` и `release/1.0.0-beta1.toml` точными HEAD зависимостей. Сохраните выведенный SHA codestyle: он передаётся отдельным входом CI. Коммит продукта делается последним. До запуска Actions все семь исходных коммитов (продукт, четыре компонента, логотип и codestyle) должны быть доступны на GitHub. Подготовка локальных коммитов не разрешает push или запуск workflow. Workflow запускается только с `main`; исходники компонентов берутся из определения версии, а не из вершин их веток.

## Настройки GitHub

Создайте защищённое environment `beta1-build`, разрешите только `main` и настройте подтверждение запуска доверенным сопровождающим. В environment разместите новые ключи только для CI, закодированные в base64 без переносов:

| Secret | Содержимое |
| --- | --- |
| `VOBOOST_BETA1_AGENTS_SIGNING_KEY` | 32 байта исходного Ed25519 seed каталога агентов |
| `VOBOOST_BETA1_PRODUCT_SIGNING_KEY` | 32 байта seed продукта |
| `VOBOOST_BETA1_NATIVE_EXECUTABLE_SIGNING_KEY` | 32 байта seed нативных программ |
| `VOBOOST_BETA1_RESTORE_SIGNING_KEY` | 32 байта seed восстановления |
| `VOBOOST_BETA1_ANDROID_KEYSTORE_BASE64` | Новый `app.jks` только для CI |

Четыре Ed25519 ключа должны отличаться. Публичные ключи и SHA-256 Android-сертификата закреплены в `release/beta1-build-public-roots.json`. Перед записью Ed25519 seed helper сверяет все четыре производных публичных ключа и настоящий сертификат из JKS с этим файлом; при несовпадении сборка останавливается и временный каталог удаляется. Формат authority сохраняет контракт сборщика: alias Android-ключа `voboost`, пароль хранилища и ключа `changeit`. Другой пароль этот build entrypoint пока не поддерживает. Ключи создаются отдельно для CI; после передачи в GitHub их приватные локальные копии удаляются. Workflow сам ключи не генерирует. Приватные материалы не попадают в репозиторий или артефакты; каталог authority удаляется отдельным шагом `always()`.

Для публичных репозиториев достаточно стандартного GitHub token. Если репозитории или submodule закрытые, добавьте repository secret `VOBOOST_SOURCE_READ_TOKEN` с правом чтения Contents ровно нужных репозиториев и submodule. Этот token нужен также заданиям упаковки вне environment. Разрешите GitHub Actions и использованные закреплённые Actions. Workflow получает только `contents: read`; права публикации ему не нужны.

## Текущая настройка и переход с dev-сборок

20 октября 2026 окружение `voboost/voboost → beta1-build` настроено: только ветка `main`, обязательное подтверждение `vithar`, пять новых CI-only secrets. Публичные корни и отпечаток Android-сертификата записаны в `beta1-build-public-roots.json`. Приватные временные файлы и найденные локальные копии старой release authority удалены. Повторно создавать или переносить прежние dev-ключи не нужно.

DMG242 остаётся проверенным пакетом с прежними dev-подписями. Новая CI authority меняет также Android-сертификат и корни доверия продукта: перед установкой первой CI-сборки полностью удалите dev-версию её прежним установщиком и дождитесь проверки очистки. Затем устанавливайте CI-комплект. OTA-переход между этими authority не заявляется.

## Запуск после коммитов и push

Откройте Actions → **Beta1 build artifacts** → Run workflow, выберите `main` и передайте полный SHA codestyle. Подтвердите environment, если требуется. Это инструкция для последующего запуска; сама подготовка workflow его не запускает.

Подписывающее задание строит closure через `tools/release/build-closure.ts` в режиме `exact-source`, проверяет подписи, встроенные корни доверия, версию и неизменность исходников. Отдельные задания macOS, Windows и Linux получают готовый closure, публичные корни и подписи проверочных сообщений; приватных ключей в этих заданиях нет. Упаковкой и повторным открытием готовых файлов владеет `voboost-installer/src/build/ci-package.ts`.

Скачивайте `beta1-build-macos`, `beta1-build-windows`, `beta1-build-linux`. Соответствующие исходники проверяются как внутренний вход сборки; отдельный архив рядом с установщиком не создаётся. В macOS DMG нет архивов и деревьев исходников; читаемые лицензии и notices остаются в приложении. `beta1-build-inputs` хранит closure, исходные SHA, состав файлов, сведения об APK и инструментах сборки; это диагностический артефакт. Срок хранения — 14 дней. Успех CI необходимо подтвердить первым реальным запуском после push и настройки secrets: локальные проверки workflow этого не заменяют.

## Отдельная публикация

Существующие `beta1-ci.yml`, `beta1-evidence-ingest.yml`, `beta1-publication.yml` и `1.0.0-beta1-trust.json` не ослабляются. Их production trust и подтверждения приёмки по-прежнему нужны для их собственного процесса публикации. Build-only workflow использует отдельную CI authority и не превращает неподготовленный production trust в разрешение на публикацию.
