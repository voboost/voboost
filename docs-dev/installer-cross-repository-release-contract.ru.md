# Межрепозиторный контракт выпуска

[English](installer-cross-repository-release-contract.md) | **Русский**

## Владение

`voboost` владеет версией продукта, source definition, защищённой подписью, сборкой полного продукта, координацией пакетов установщика, доказательствами и публикацией. `voboost-app`, `voboost-agents`, `voboost-inject` и `voboost-installer` проверяют и собирают собственные исходники, но не публикуют независимые выпуски компонентов.

Source definition содержит полный точный commit каждого component repository. Ветка, короткий commit, плавающий tag, локальный путь и последний доступный artifact не могут задавать вход выпуска.

## Результаты сборки компонентов

Каждый компонент предоставляет неинтерактивную команду проверки и product-neutral adapter для сборки неподписанных входов. Adapter возвращает только точные именованные байты компонента и не получает закрытый ключ, не создаёт metadata продукта, tag или release, не загружает artifacts, не публикует канал и не отправляет межрепозиторные события.

Для beta1 `voboost-inject/tools/prepare-beta1-unsigned.sh` экспортирует десять плоских native-входов. `voboost-app` экспортирует один неподписанный APK. `voboost-agents` экспортирует `agents.json`, `agent-common.dex` и все target-specific `agent-*.dex`. `voboost-installer` предоставляет проверенную реализацию платформенной упаковки.

## Сборка продукта и доверие

Release tooling продукта подписывает точный Android APK, каталог агентов, role-bound native-программы, разрешение восстановления и `voboost.json`. Полученная плоская closure проверяется как замкнутое множество: отсутствующий, лишний, повторный, переименованный, вложенный, имеющий другой размер или SHA-256 файл отклоняется.

Долгоживущие корни доверия относятся к сертификату Android, product manifest, каталогу агентов, native-программам и восстановлению. Native OTA напрямую использует `voboost.json`: второго native manifest и отдельного корня доверия для него больше нет. Desktop installer встраивает только три корня, которыми пользуется сам: product manifest, восстановление и native executable. Корень каталога агентов остаётся во встроенных проверяющих механизмах device-бинарников.

Закрытые ключи существуют только во временной локальной тестовой сборке или в защищённой задаче подписи продукта. Component repositories, обычная CI, frontend установщика, данные на машине и упакованные fixtures с открытыми ключами не содержат закрытых ключей.

## Пакеты установщика

Product pipeline упаковывает одну и ту же подписанную closure в:

```text
voboost-installer-<release>.exe
voboost-installer-<release>-arm64.dmg
voboost-installer-<release>-x86_64.dmg
voboost-installer-<release>.tar.bz2
```

Установщик не пересобирает, не скачивает, не выбирает и не заменяет байты продукта. Windows добавляет только ADB и две его DLL. macOS использует встроенный прямой ADB без внешнего executable ADB и поставляет отдельные DMG `arm64` и `x86_64`. Linux не добавляет ADB; tar.bz2 содержит `voboost-installer` с mode `0755` и закреплённые лицензии и уведомления.

## Доказательства и публикация

Для macOS комплект исходников поставляется отдельным артефактом рядом с DMG. Команда упаковки до начала сборки проверяет его по тому же подписанному product manifest, но образ и приложение не содержат `corresponding-source.tar.gz`, `corresponding-source.json` и `BUILD-MODIFIED.md`.

Host-проверки подтверждают исходники, схемы, детерминированную сборку, подписи и структуру пакетов. Emulator, device, автомобиль, защищённая CI и публикация остаются отдельными уровнями доказательств.

Для beta1 действует фиксированный порядок: локальная сборка с временными ключами, проверка на физической машине, доказательство чистого удаления, согласованные commits и push, сборка в CI, проверка точных CI-пакетов на машине и отдельное решение о публикации. До этого решения нельзя публиковать GitHub Release, release assets и указатель OTA-канала.

## Упаковка в CI без секретов

После сборки продукта центральный workflow вызывает `node src/build/ci-package.ts <macos|windows|linux> <bundle-root> <public-inputs> <output>` в checkout точного коммита установщика. Каталог сборки содержит `closure/` и `inputs/observation/` из проверенной сборки продукта. `VOBOOST_PRODUCT_VERSION` должен совпадать с версией замыкания и исходников установщика.

Каталог публичных входов содержит ровно `product.pem`, `restore.pem`, `native-executable.pem`, `product.fixture.sig`, `restore.fixture.sig` и `native-executable.fixture.sig`. Контрольные подписи создаёт продукт; упаковка не получает закрытые ключи. Подписываются UTF-8 строки `voboost-role-trust-fixture-v1:release-catalog`, `voboost-role-trust-fixture-v1:restore` и `voboost-role-trust-fixture-v1:native-executable`, каждая с одним LF в конце.

Перед вызовом адаптера платформенные runner устанавливают зависимости npm по lockfile и Rust 1.98.0. macOS требует обе Apple-цели Rust; Linux — цель GNU x86-64, `bzip2` и инструменты из `scripts/verify-linux-cli.sh`. Windows собирает переносимый desktop EXE, Linux — только CLI, macOS — универсальный вход приложения и отдельные DMG `arm64` и `x86_64`. Каждый пакет использует подписанное замыкание и проверяет встроенные корни доверия и CLI упакованного установщика. Адаптер удаляет собственный промежуточный каталог после успеха и сохраняет общий кеш Cargo. При ошибке каталог сохраняется для восстановления монтирований и диагностики. Он не публикует пакеты и не запускает эмуляторные тесты.
