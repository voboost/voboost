# Как внести изменение

[English](contributing.md) | **Русский**

Изменение должно сохранять пользовательское поведение, границы доверия и возможность полного удаления. Начинайте с документации пользователя и применённого OpenSpec, а не с удобного места в коде.

## Выбор задачи

Для агента откройте [статус агентов](agents-status.ru.md): там указаны статус, процессы, применимость, требования OpenSpec со статусом `Unverified` и следующий вклад.

beta1 состоит из семи агентов со статусом `stable`, агента `logs` со статусом `unstable` и 35 агентов со статусом `planned`. Изменение статуса требует изменения метаданных, каталога агентов, Settings projection, документации, OpenSpec и проверок состава.

Для системной части сначала определите владельца:

- product schemas, release definitions, publication и docs — `voboost`
- приложение — `voboost-app`
- агенты, reflection runtime и OEM stubs — `voboost-agents`
- демон, native-код и системные операции — `voboost-inject`
- GUI/CLI/packaging — `voboost-installer`

## Перед изменением

1. Прочитайте пользовательскую страницу функции
2. Прочитайте страницу разработчика для компонента
3. Прочитайте полный OpenSpec requirement
4. Найдите исходное описание и его генератор
5. Проверьте незакоммиченные изменения и не затрагивайте чужую работу
6. Воспроизведите ошибку или сформулируйте новое наблюдаемое поведение

## OpenSpec

Изменение поведения начинается с одного change в OpenSpec, ограниченного задачей:

1. `proposal` — зачем и что меняется
2. `design` — решения и границы
3. `tasks` — проверяемые шаги
4. `delta spec` — добавленные, изменённые и удалённые требования
5. strict validation
6. реализация
7. именованные Gates
8. применение и перенос в архив
9. повторная strict validation

Только rebaseline текущего состояния выполняется без change flow и только по явному решению владельца проекта.

## Новый агент

Создайте один пакет:

```text
ru/voboost/agents/<feature>/
├── <Name>Agent.java
├── <Name>Agent.json
├── <Name>Agent.md
├── <Name>Agent.ru.md
├── <Name>Contracts.json
└── <Name>*.java
```

Правила:

- ID — канонический kebab-case
- пакет Java — `ru.voboost.agents.<feature>`
- каждый частный файл использует полный префикс `<Name>`
- имя — кратчайшее из однозначных
- JSON метаданных — четыре пробела
- агент со статусом `planned` использует `status: planned` и отключённую активацию
- рабочий код агента — Java 8 без Kotlin, AndroidX и лямбда-выражений
- общие классы среды появляются только при доказанной общей ответственности

## Контракт агента

1. Опишите стабильные пакеты, процессы, классы, members и descriptors
2. Не используйте SHA APK, сертификат, версию прошивки и имена, появившиеся только после декомпиляции
3. Добавьте положительный и отрицательный варианты возможностей
4. Скомпилируйте JSON в неизменяемые типизированные определения
5. Добавьте debug-запись для каждого шага проверки
6. Требуйте ровно одно полное совпадение

Если метод или поле могло быть переименовано обфускацией, используйте descriptor/modifiers/unique structural binding либо оставьте контракт Unverified. Не угадывайте имя.

Не переносите в репозиторий OEM APK, декомпилированные исходники, их бинарные отпечатки или локальные пути. Результат исследования оформляется как минимальный декларативный контракт, вариант stub, положительный и отрицательные тесты и честная граница `Unverified`.

## Действие и подтверждение

Агент должен отдельно описать:

- что читает до изменения
- что сохраняет как исходное состояние
- одно разрешённое действие
- ACK
- контрольное чтение
- повтор
- stop
- восстановление
- поведение при частичном отказе

Успешная установка перехвата ещё не означает успешную работу функции.

## Заглушки

Заглушка сохраняет точные FQCN, descriptors и modifiers. Добавляйте только метод или поле, нужные тесту. Заглушка не содержит упрощённого вспомогательного кода и никогда не подключается к рабочей сборке.

Для неодинаковых контрактов создайте разные варианты возможностей, а не одну слишком широкую заглушку.

## Состояние

Агент использует RPC состояния демона и только собственные ключи. Нельзя писать SharedPreferences или файлы штатного приложения.

Если исходное значение не сохранено, uninstall не должен придумывать его.

## Документация

Сначала обновите русский документ:

- назначение
- пользовательский результат
- применимость
- целевой процесс
- контракт
- действие и контрольное чтение
- состояние
- остановку и удаление
- диагностику
- доказательства и Unverified

После утверждения русского текста синхронизируйте английскую версию. Точные идентификаторы не переводятся.

Пользовательское изменение дополнительно обновляет пользовательские страницы, roadmap и changelog. Каждый выпуск получает свой слоган.

## Проверки

Минимум для агента:

- метаданные и схему
- contract compiler
- positive match
- zero match
- ambiguous match
- hook/action
- ACK/readback
- stop/restore
- invalid input
- варианты заглушек
- docs/OpenSpec
- full `./gradlew check`

Host-тесты не заменяют проверки на устройстве и в автомобиле. Оставьте непроверенные требования со статусом `Unverified`.

Команды из корня репозитория агентов:

```bash
./gradlew check
./gradlew buildRelease
```

Код агента и runtime находится в `voboost-agents/src/main/java/ru/voboost/agents`, host-тесты — в `voboost-agents/src/test/java/ru/voboost/agents`, заглушки — в `voboost-agents/stubs`, capabilities — в `voboost-agents/openspec/specs`. Подробности native-внедрения находятся в [native runtime](native.ru.md), а не дублируются в документе агента.

## Именование

Кратчайшее однозначное имя важнее подробного пересказа контекста:

```text
install-app
```

Уточнение добавляется только для различения соседних понятий.

## Коммит

Один коммит содержит одно завершённое изменение:

- OpenSpec
- код
- тесты
- сгенерированные файлы, если они хранятся в Git
- документацию RU/EN
- changelog при пользовательском изменении

Формат:

```text
<type>(<scope>): <summary>
```

Не включайте несвязанные изменения форматирования, локальные артефакты, закрытые ключи, абсолютные пути, сырые исследовательские материалы или прежние отчёты о проверках.
