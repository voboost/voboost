# Тестирование и доказательства

[English](testing.md) | **Русский**

Каждый результат называет точные revision, artifact, environment, action и observable outcome. Host-, emulator-, device- и vehicle-gates независимы.

| Gate | Доказывает | Не доказывает |
| --- | --- | --- |
| Host | parsers, schemas, build graphs, identity финальных байтов, package structure | Android- и OEM-runtime |
| Emulator | install/update/reboot/recovery на указанном rooted Android image | OEM contracts автомобиля |
| Device | PackageManager, root, init, SELinux, ptrace, ART на указанном hardware | vehicle UI, CAN, audio и поведение в движении |
| Vehicle | поведение точного выпуска на указанной модели и прошивке | другие модели и прошивки |

## Отдельный инструмент прогонов эмулятора

Обычный установщик использует один параметр `--device` для USB автомобиля и подготовленного эмулятора. Наблюдения UI, сценарии снимков и управление искусственными сбоями выполняет инструмент `emulator-driver` из корневого `tests/emulator/driver/adb`. Эти команды не входят в установщик или DMG. Компиляция бинарника установщика с тестовой feature запрещена.

Эмуляторные задачи Gradle собирают инструмент задачей `compileEmulatorDriver`, используя установленный Android SDK и общий release-кеш Cargo. Путь к SDK задаётся через `ANDROID_SDK_ROOT` или `ANDROID_HOME`; задача выбирает Java 17. Отдельные Node-прогоны используют тот же исполняемый файл из кеша либо абсолютный путь `VOBOOST_EMULATOR_DRIVER`.

Закрытый вызов: `emulator-driver --emulator-check /absolute/request.json --device emulator-5588 --candidate /absolute/voboost-installer`. Инструмент отвергает USB serial и некорректные адреса эмулятора. Проверку комплекта выполняет сам выбранный обычный установщик. Штатное удаление передаётся ему через публичную операцию `--uninstall --device`; доказательства наблюдений и сбоев связываются с обоими исполняемыми файлами. Установка и обновление по-прежнему запускают обычного кандидата напрямую. Host-тесты не подтверждают живой прогон эмулятора.

## Host-gates компонентов

`voboost-app` проверяет headless manifest, ownership JobScheduler, download/crypto paths, socket transport, evidence package/version/signer APK и minified inventory.

`voboost-agents` проверяет Java compilation, D8, точный target placement, catalog/signature, stubs, lifecycle, динамические OEM surfaces и отклонение прежних `ui-res` inputs и numeric OEM resource profiles. Отдельные проверки ресурсов перевода описаны в [инструментах перевода](translation-tooling.ru.md).

`voboost-inject` проверяет Cargo/C/C++, operation contracts, APK identity, process admission, ptrace rollback, role signatures, полную активацию продукта, SELinux policy и Android cross-build.

`voboost-installer` проверяет frontend/Rust behavior, startup routing, typed management, CLI routing, offline runtime и точную структуру пакетов Windows, macOS и Linux.

`voboost` проверяет source definitions, реальное извлечение APK identity через pinned tooling, отклонение подменённого evidence при неизменных APK bytes, Draft 2020-12 и semantic manifest conformance, hashing точного closure, automatic reuse, canonical restore production/signature/staleness, структуру docs, links, language pairs и formatting.

В режиме без изображений нормализация первой страницы приложений использует закрытый запрос `launcher-page-observe` с двумя независимо созданными 64-hex nonce. Парные root receipts связывают прямые метрики внутренней сетки, окно основного экрана с фокусом и время жизни процесса и поколения; независимые наблюдения загрузки и Accessibility captures до запроса, после него и перед следующим жестом сопоставляют реальные подписи и границы. Конкретный native `AllAppBarView` представлен в захваченном Accessibility дереве классом `androidx.recyclerview.widget.RecyclerView`; это разные профили. Пустой список включённых агентов не отключает общий endpoint наблюдения. Режим с разрешёнными изображениями сохраняет проверку PNG indicator. Case 12 сначала наблюдает выключенный launcher checkbox из подписанного каталога, захватывает исходную сетку без fixture и проверяет отсутствие выбранной launcher injection в независимом resident status, затем включает агент. Включённый или недоступный для наблюдения checkbox оставляет результат unavailable без автоматического сброса. Исходный stock capture case 1 до установки не меняется. Host-тесты dispatcher и некорректных receipts не подтверждают runtime case 12 с перетаскиванием и перезагрузкой или визуальную приёмку; для этого остаются отдельные runtime gates.

## Cross-system release gates

До публикации один точный closure должен пройти clean component builds, signature и inventory checks, draft re-download, offline package tests Windows/macOS/Linux, rooted Android 9 emulator flows, проверки указанного device с SELinux Enforcing и все vehicle-gates из source definition.

Результат host-gate не заменяет обязательный emulator-, device- или vehicle-gate.

## Проверка CLI через Voyemu

Единый [чек-лист приёмки beta1](../release/BETA1-CHECKLIST.md) задаёт порядок проверки замечаний, критерии закрытия и ссылки на доказательства. Все 27 обязательных кейсов перечислены в [исполняемом плане](../release/beta1-functional-plan.json).

`release/run-emulator-beta1-gate.sh` выполняет 27 функциональных кейсов через проверенный CLI установщика и официальный Voyemu status/verify. Требуется подготовленная, уже запущенная машина с переданным runtime lease; PID/порт сохраняются, runner не запускает, не останавливает, не перезапускает и не пересобирает машину. Закрытый конфиг и schema3 описаны в [release tooling](../release/README.md). Direct ADB, произвольные shell/scripts, координатные presets и fault cuts исключены. Каждая guest-загрузка, включая промежуточные загрузки установщика, требует независимой полной проверки inventory профиля, Enforcing и свежего UI; пропущенное окно остаётся unavailable. Недоступные CAN/catalog/locale/provenance и visual review не превращаются в pass. Host fixtures и исторические manual receipts не доказывают готовность runtime.

Одна команда `release/run-emulator-beta1-gate.sh /absolute/config.json` выполняет существующий автоматический прогон и сохраняет `report.md` в каталоге `output`, в том числе при отказе. Отчёт разделяет failed, unavailable и not-run, показывает каждый кейс и subcheck, записанную длительность, загрузки, логи и снимки. Непроверенные визуальные пункты остаются pending; отчёт не превращает их в pass. Ошибка отчёта не скрывает ошибку прогона.

Перед кейсом 1 отдельная подготовка через упакованный CLI `--uninstall` сохраняет полный receipt девяти проверок, результат normal/already-absent/emergency и точные package/runtime/boot. Аварийное удаление может подтвердить только эту подготовку. Кейс 1 проверяет свежий чистый статус и устанавливает; кейс 2 требует штатного CLI-удаления и проверенной новой загрузки. Кейс 3 ссылается на тот же action receipt кейса 2 и требует свежего absent status, Inspect, полной проверки профиля и UI capture на той же загрузке без повторного удаления. Кейс 17 по-прежнему требует собственного заранее запущенного observer и строгого штатного удаления. Кейс 24 ссылается на реальное доказательство подготовки отдельно от начальных OEM/CAN inputs и present false root readback; отсутствие доказательства остаётся unavailable. Старые schema1/2 receipts не удовлетворяют schema3.

Runner отдельно записывает фиксированные offline host-тесты agents с актуальными JUnit XML и снимками исходников, совпадающими с source-build receipt closure. Copy берётся из фактических production APIs и сверяется с исходниками, подписанным metadata и всеми DEX комплекта. Обычный `--logs` выгружает ограниченный tar.xz, а `--diagnostics` выводит ограниченную JSON-квитанцию. Свежие записи той же загрузки и root-state triad остаются отдельными наблюдениями; absent/unavailable не означают false. Cold/warm EV/PW используют штатные OEM controls и закрытые Reboot/Sleep/Wake. Первичное seeding проверяется на обычных FEV=false/PW=true; остальные начальные входы относятся только к host-проверкам. Passive locale/layout measurements не заменяют просмотр PNG; реальные error/outage branches и отсутствующие visual доказательства остаются отдельными unavailable subchecks.

Текущий потребитель также сохраняет canonical daemon `vehicle-state-observed` для двух фиксированных armed keys с resident generation, каталогом, зарегистрированным временем жизни endpoint и точным доступным desired revision. Receipt доказывает момент реальной операции; историческая запись не становится свежим запросом. Перенос read baseline требует полного окна одной загрузки без противоречащих операций и свежего CAN restore. Диагностика через stock su может оставаться unavailable. Desktop install preparation требует реальных упорядоченных DEBUG receipts из однозначного stderr установщика для того же install action; диагностический driver включает `VOBOOST_LOG=debug` для этого действия. Квитанции должны подтверждать успешные source-bound Root/Remount/Permissive/system-write steps, затем нужны независимые Enforcing boot observations; ранее принятый journal не означает свежий boot readback. Startup cases используют реальные Settings radio, все девять выбранных описаний и возврат из none только через компьютер. Одобренный Voboost Fixture удаляется после наблюдений кейсов 12/18 только при доказанном исходном отсутствии и успешной установке точных bytes; проверяются свежее отсутствие и сохранённые OEM labels, а незавершённое или недоказанное удаление сохраняется отдельно.

## Синтетические шрифты для тестов

Четыре TTF в `voboost-agents/src/test/resources/font/cyrillic/` — оригинальные материалы Voboost под MIT этого репозитория. Они используют числовые метрики и четырёхточечные прямоугольники, а не контуры внешнего шрифта. В каждом есть `.notdef`, 66 отдельных русских отображений, десять таблиц SFNT, корректные простые контуры и контрольные суммы. Regular использует format-12 cmap/long loca, semibold — format-4 cmap/short loca. Исправленные пары меняют 64 и 63 метрики соответственно, сохраняя намеренно широкие прямоугольники. Они построены независимо от production patcher.

`FontCyrillicFixtureCommitmentTest` независимо проверяет идентичность, каталог SFNT, отображения, контуры, метрики, допустимые изменения байтов и контрольные суммы. Прежнего генератора fixture в текущих исходниках нет; поддерживаемой команды регенерации нет. Сохраняйте зафиксированные материалы и проверяйте замену по независимому oracle.

Production-допуск точного шрифта отклоняет эти синтетические входы. Необязательные OEM-тесты используют отдельно полученные `regular-defective.ttf`, `regular-corrected.ttf`, `semibold-defective.ttf`, `semibold-corrected.ttf` в локальном каталоге проекта вне репозиториев исходников. Из `voboost-agents` выполните `./gradlew :test :stubs:settings:testReleaseUnitTest -PoemFontFixturesDir=/absolute/project-local/font-fixtures`. Явно заданные отсутствующие или неверные входы отклоняются; без свойства точные OEM-тесты пропускаются, а Settings использует синтетические ресурсы. Опция не даёт прав на распространение внешних шрифтов или содержащих их APK. Host-результат не подтверждает отрисовку на устройстве.

Корневая задача `testDesiredOwner` владеет JSON-сценариями в `tests/integration/daemon/` и вызывает проверку настоящего RPC владельца через существующую сборку Cargo. Команда: `./gradlew --offline testDesiredOwner -Pcargo=/absolute/cargo -Prustc=/absolute/rustc`. Проверка требует фактическую квитанцию и проверяет сохранение OFF при блокировке продукта и согласовании значений по умолчанию, перезапуске владельца и новой загрузке, а также отклонение устаревшего ON после последнего OFF. Эта интеграционная проверка на хосте не доказывает доставку в Android или показ Saved в интерфейсе. Отдельный сценарий `testVehicleOnly` задаёт OFF обычной галочкой Settings, выполняет Sleep/Wake и холодный Reboot для PW и FEV, затем проверяет сохранённый выбор, отсутствие опубликованных целей, свежие OEM-контролы и CAN getters. Его unit-тесты с фикстурами проверяют только порядок действий и отклонение недостоверных наблюдений. Ввод во время блокировки установки, перезапуск владельца и доставка устаревшей квитанции Saved остаются заблокированными на этом уровне runtime до появления допущенных API наблюдения и управления; выборочные getter-чтения не доказывают непрерывный CAN OFF.

## Корневые команды Gradle

Из репозитория продукта `./gradlew --offline unitTest` запускает root Java unit и компонентные unit-наборы через инструменты их владельцев; для выбора тестов добавьте `--tests <pattern>`. `./gradlew --offline buildProduct -Pconfig=/absolute/build.json` передаёт управление существующему сборщику `tools/release/build-closure.ts` с теми же требованиями к конфигурации и полномочиям. Сборка — отдельная операция, которая может использовать ключи подписи; сама команда не даёт разрешения на сборку или подпись.

`./gradlew --offline integrationTest` и `./gradlew --offline emulatorAcceptance` выполняют реализованные host- и emulator-наборы. Их выполнение само по себе не подтверждает полную приёмку: `./check-candidate` проверяет предусловия и обязательные evidence каждого case/target. Java-тесты разложены сначала по слою (`tests/unit`, `tests/integration` или `tests/emulator`), затем по владельцу. В `generic` лежат общие проверки, в том числе `GenericAssertViewTest` и `GenericCandidateDmgTest`. Для установщика используются `installer-cli` и `installer-gui`. У приборки и отдельных агентов есть свои группы с тестовыми данными. Gradle компилирует `tests/common` и `tests/emulator/driver` для координатора и тестовых наборов. Offline-запуск требует уже закешированного Gradle 8.9. Unit-отчёты сохраняются в `build/reports/tests/unitTest` и `build/test-results/unitTest`; продуктовые отчёты конкретного запуска описаны ниже.

`integrationTestFocused` запускает ограниченную диагностическую проверку DMG macOS с явно заданным локальным публичным ключом: `-PtrustScope=local-input`, абсолютные `-PcandidateDmg`, `-PproductPublicRoot`, `-Pcargo`, `-Prustc`. Требуются доверенные локальные инструменты и стабильные исходники продукта и контрактов; Cargo работает offline и locked, с явно выбранной host-целью и общим кешем компиляции; отдельная копия verifier удаляется после проверки. Эта проверка не доказывает происхождение ключа или кандидата и не устанавливает production trust. Без явной области доверия команда возвращает BLOCKED. `integrationTest` выполняет проверки комплекта, реальных producer/consumer, транзакций и восстановления, интерфейса и логов. Общий runner требует успешные результаты I01–I05 текущего запуска; отсутствие доказательства не считается успехом.

Сценарий проверяет product closure штатным release verifier. Для лицензий установщика и `icon.icns` проверяются наличие и тип regular файла, но не содержимое; остальные свойства полного пакета и production trust не подтверждаются. Cargo получает `--offline`; этот флаг не изолирует от сети rustc или build scripts. Описанный локальный trust input не является source-pinned CI root.

## Этапы тестирования в эмуляторе

Для прогона реализованных сценариев выполните `./gradlew --offline emulatorCheck -PcandidateDmg=/absolute/current.dmg -PpreviousDmg=/absolute/previous.dmg`. Предыдущий DMG нужен для проверки обновления. Если он не указан, остальные сценарии выполнятся, а итог прогона будет неполным.

Общий `config/config-voyemu.json` задаёт роли машин `installer` и `agents`. Локальный `config/config-voyemu-local.json` сопоставляет имена машин с путями. Если настроена одна машина, обе роли используют её. Когда пути совпадают, сначала проходят тесты установщика, затем на той же машине готовится установленный кандидат для тестов агентов. Разные канонические пути позволяют запустить группы параллельно. Обе группы используют один образ текущего DMG, смонтированный только для чтения. Voyemu запускает сессии по очереди, затем обе машины работают одновременно. Чтобы явно выбрать одну машину, укажите `-PmachineName`.

| Задача | Что делает |
| --- | --- |
| `emulatorPrepare` | Готовит состояние диска для одной группы и завершает служебную сессию. Тесты установщика начинают со штатной системы. Для тестов агентов этап устанавливает, обновляет или переиспользует выбранную сборку. |
| `emulatorStart` | Запускает тестовую сессию, дожидается готовности Android и подтверждения доставки от QNX, если он нужен, и сохраняет идентификатор сессии. |
| `emulatorTest` | Выполняет выбранные сценарии в сохранённой сессии. |
| `emulatorReconcile` | Только читает поддержанные постусловия сохранённой операции, без повторного ввода. Предыдущий неуспешный тест остаётся неуспешным. |
| `emulatorStop` | Восстанавливает настройки, изменённые при подготовке сессии, останавливает её и после подтверждения отключает образы. |
| `emulatorCheck` | Выполняет все четыре этапа и собирает результаты выбранных групп. |

Для группы добавьте `-Psuite=agent-pedestrian-warning`. Для одного сценария добавьте `--tests '*AgentPedestrianWarning.hidesOffIconFromDrawer'` к `emulatorCheck` или `emulatorTest`. Флаг `--test-dry-run` выводит выбранные сценарии без запуска Voyemu. Группе `generic` не нужны DMG и QNX.

`AgentPedestrianWarning.keepsSoundDisabledAndIconsUnchangedAfterMultimediaRestart` выбирает OFF через штатную шторку, сверяет независимое CAN-состояние и сохранённый выбор, сравнивает область приборки с принятым эталоном и снимает реальный значок шторки. После перезагрузки мультимедиа он наблюдает OFF без повторного переключения и повторяет обе проверки изображений. Изображения OFF в шторке должны попиксельно совпадать до и после перезагрузки и отличаться от ON. Этот сценарий не подменяет тестовый вход звука QNX. Неизвестный ввод сохраняет владельца до поддержанного продолжения только чтением; неподдержанные постусловия отклоняются.

При раздельном запуске указывайте одинаковые параметры группы, машины и DMG на каждом этапе. Закрытые служебные записи и отчёты сохраняются в `build/emulator-work/lifecycle` или внутри каталога из `-PcheckWorkDir`. Выполните `emulatorStop` после отдельного теста, даже если он упал. При неизвестном исходе операции сохраняются сессия и журналы для разбора. На выделенной тестовой машине `-PprepareExisting=uninstall` разрешает удалить прежнюю установку, если это требуется для подготовки.

## Адресная проверка жизненного цикла Voyemu

Gradle-раннер читает идентификаторы машин из `config/config-voyemu.json`, а локальные пути — из игнорируемого `config/config-voyemu-local.json`; скопируйте `config/config-voyemu-local.example.json` и укажите реальные пути. Выберите объявленную машину через `-PmachineName=free-09-chinese-20260106-6.0.3` и задайте `-Pscenario=fresh` или `resume`. `-Pvoyemu` и `-Pmachine` переопределяют локальные пути. Профиль API определяется по runtime manifest выбранной машины. Автоматического выбора машины нет. Отдельный TypeScript-раннер релиза сохраняет собственный контракт конфигурации и сессии.

`emulatorFocused` выполняет выбранные реальные сценарии schema 1 отдельно от незавершённого общего реестра приёмки. Выберите настроенную машину или укажите абсолютные `-Pvoyemu` и `-Pmachine`, а также явный сценарий состояния автомобиля `-Pscenario=fresh` либо `resume` и фильтр `--tests '*SessionLifecycleTest'`. Сценарий запускает явно выбранную подготовленную машину в фоне без QNX, проверяет готовность Android и непустое дерево `session.ui` основного экрана, затем подтверждает остановку собственной сессии. Он не устанавливает Voboost и не доказывает работу агентов. Полный `emulatorAcceptance` остаётся BLOCKED.

Перед отправкой запрос получает необратимое сохранённое резервирование и одноразовый допуск. При потере ответа на изменение выполняется только `operation.get`; исходное изменение не повторяется. Неизвестный исход или неподтверждённая очистка означают провал проверки. Токены сессии и JSON-доказательства сохраняются с закрытыми правами в `build/emulator-work/session-*`; перед удалением каталога сохраните полезные результаты. Сценарий не останавливает чужую сессию и не пересоздаёт подготовленную машину. Перед запуском координатор должен выделить машину и проверить свободное место и отсутствие чужого владельца. Исходники, API, host-тесты и эмулятор дают разные уровни доказательств.

## Адресный жизненный цикл установщика из DMG

Отдельный Java-сценарий `--tests '*InstallerCliLifecycleTest'` использует настоящий DMG macOS, а не самостоятельный CLI или специальную сборку для разработки. Помимо общих входов Voyemu нужны абсолютный `-PcandidateDmg` и явный `-PwithCluster=true`. QNX работает до остановки тестовой сессии. Профиль должен совпадать с манифестом подготовленной машины. Сценарий запускает выделенную машину в фоне с Android и QNX, проверяет начальную готовность Android/UI и получает точный `--device` из статуса собственной сессии. USB-устройство по умолчанию не выбирается.

По умолчанию `prepareExisting=require-absent` запрещает продолжать при существующей установке. Только на выделенной тестовой машине явный `-PprepareExisting=uninstall` запускает штатное удаление перед новой установкой. Подготовка записывается отдельно. Аварийная очистка, отсутствие независимого пассивного наблюдения удаления или недоступная приборка не превращаются в успешную подготовку.

Сценарий монтирует кандидат только для чтения, проверяет codesign и штатную проверку пакета, затем связывает протокол установки с фактическими подписанными байтами манифеста и каталога. Перед явным status/accept проверяются потоковый arm, идентичность и номер промежуточной загрузки, Enforcing, готовность обоих Android-экранов, положительно наблюдаемые окно и узлы Launcher на основном экране и повторная проверка той же загрузки. Неудачная проверка загрузки отклоняет только доказанную ожидающую попытку. Частичные метаданные посторонних окон не доказывают полноту дерева или отсутствие нужного элемента.

После установки требуются совпадающие healthy management и текущая публикация демона в той же загрузке. Затем выполняется одна сохранённая тёплая перезагрузка без повторной отправки после неизвестного исхода, повторная проверка готовности, штатное удаление с девятью проверками и независимые наблюдения отсутствия management/root. Этот базовый цикл не доказывает функциональность каждого агента, обновление прежнего выпуска, GUI или полный цикл агентов QNX. Общий `emulatorAcceptance` остаётся заблокирован незавершённым обязательным реестром.

Раздельные исходные stdout/stderr CLI, ограниченные DeviceReport, журналы владения/перезагрузки и `result.json` сохраняются в закрытых каталогах `build/emulator-work/installer-*`. Обработчики CLI получают отзываемую область с монотонным сроком; реальные внешние действия проверяют её перед отправкой. Истечение срока отменяет обработчики и завершает захваченные собственные helper-процессы. Неподтверждённое завершение обработчика/helper означает провал с сохранением доказательств. Helper монтирования имеет отдельный срок жизни до подтверждённого detach. Изменения с неизвестным исходом не повторяются.

`./gradlew emulatorFocused --tests '*InstallerCliLifecycleTest' --offline -Pvoyemu=/absolute/voyemu -Pmachine=/absolute/prepared-machine -Pscenario=fresh -PcandidateDmg=/absolute/candidate.dmg -PwithCluster=true -PprepareExisting=uninstall` запускает этот диагностический сценарий после выделения машины и проверки ресурсов координатором. Отсутствующие входы и недоступные наблюдения приводят к провалу; компиляция сценария не является runtime-приёмкой.

Завершающее удаление в lifecycle открывает реальное действие удаления в Settings и подтверждает OEM-диалог после готовности наблюдателя из пакета. Ограниченный ввод использует свежие наблюдаемые контролы; журнал мутации остаётся незавершённым, пока новый Enforcing boot, квитанция девяти проверок и независимое наблюдение отсутствия не согласуются. Наблюдатель требует уже доступный root и не включает root, не перемонтирует разделы, не перезапускает систему и не ослабляет политику. После очистки собственной fixture Voboost Fixture должен уже отсутствовать; ошибка package manager блокирует сценарий, а не доказывает отсутствие. Host-проверки UI/парсеров и компиляция не означают приёмку в эмуляторе.

Сценарий stable-checkbox берёт контролы и правила конфликтов из проверенного каталога кандидата. Он выполняет реальные OFF/ON-нажатия, сверяет наблюдаемое состояние публичного Checkbox с полной канонической desired-конфигурацией, проверяет оба направления конфликта клавиатур и восстанавливает исходную конфигурацию после успешной проверки. Неподтверждённые мутации сохраняют незавершённую durable-операцию для read-only reconciliation. Эффекты агентов остаются отдельными требованиями. Отдельная ветка отказа startup-radio использует существующее ограниченное diagnostic window, точную корреляцию с root fault-effect и EOF cleanup; она не завершает case23 без evidence обязательных языковых веток и отмены.

## Владение машиной и незавершённые операции

`MachineLease` связывает один root runner с каноническим путём собранной машины, включая алиасы пути. `ProductRun` до отправки операции сохраняет приватный durable journal и не разрешает следующую мутацию или остановку гостя, пока dispatched-операция не получила проверенный terminal результат. Неизвестный исход сохраняет owner record для последующего reconciliation; новый запуск не подменяет его новой установкой. Это не заменяет проверку remote ownership через Voyemu.

`AcceptancePlan` расширяет существующий `release/beta1-functional-plan.json` по targets фактического каталога кандидата. Неизвестный stable-агент, пропущенный target, отсутствующее evidence либо неподтверждённый cleanup блокируют полный verdict. Focused-отчёт не становится полной приёмкой. Эти новые пути находятся в реализации; их выполнение будет проверено после завершения пакета.

## Единый маршрут кандидата

`./check-candidate` последовательно вызывает корневые Gradle-наборы `unitTest`, `integrationTest` и `emulatorAcceptance`. Первый отказ не запускает зависимый уровень. Внутри L1 собираются результаты всех владельцев; nested Gradle tests получают `--rerun-tasks`. SDK задаётся через `ANDROID_SDK_ROOT` или `ANDROID_HOME`, NDK — через `ANDROID_NDK_HOME`, JDK — через `JAVA_HOME`; новые toolchains не скачиваются при `--offline`.

Обязательные параметры: абсолютные `-PcandidateDmg`, `-PproductPublicRoot`, `-Pcargo`, `-Prustc` и явный `-PtrustScope=local-input`. Выбор Voyemu берётся из двух файлов `config/config-voyemu*.json` и `-PmachineName`; состояние запуска задаётся `-Pscenario=fresh` либо `resume`. Для полного базового CLI-цикла нужен `-PwithCluster=true`.

Каждый запуск сохраняет отдельный `build/candidate-check/<run-id>/report.json`, исходные логи и receipts. Проверки CLI в полном L2 используют настоящий бинарник из DMG; старый standalone CLI остаётся отдельной focused-проверкой. Реестр разворачивается по каталогу проверенного кандидата. Отсутствующие I01–I05 блокируют VM; отсутствие любого обязательного функционального, GUI- или agent-target evidence блокирует полный PASS. Сейчас часть этих исполнителей ещё отсутствует: рабочая команда и успешные отдельные наборы не означают готовность кандидата.

`retireFailedFixture` явно регистрирует уже выполненный операторский stop того же failed run/session. Используется настоящий retained stop journal/lookup с verified cleanup, закрытым supervisor endpoint и освобождённым lock; новые start/stop, product mutation или reset не посылаются. Disposition — `retired-failed`, acceptance остаётся FAILED, `baselineRequired=true`. Старые failed-install и unknown-uninstall records не меняются. Generic open/resume/install на этой машине остаётся запрещён. Fresh baseline admission пока не реализован; retirement и его JUnit success не считаются normal removal или product acceptance. Требуются `scenario=resume` и исходные `resumeRun`/lease root `checkWorkDir`; DMG кандидата для этой регистрации не нужен.

Интеграционный `InstallerCliTransactionRecoveryTest` вызывает существующие production-драйверы install/restore/uninstall с подставленными transport/FS и реальный signed generation update на durable phase/crash cuts. `DaemonLogPipelineTest` выбирает текущий resident owner binary (`voboost-daemon`), выполняет exact ignored producer и framed Store test с одним selected terminal pass каждый. Одноразовый настоящий Cargo inventory сохранён как review evidence; регулярный запуск отвергает пустой фильтр по точным именам и terminal counts без повторной дорогой listing-сборки. Producer записывает больше 8 MiB настоящим owner writer, проверяет retention с host budget 8 MiB и вызывает настоящий owner export; desktop consumer сохраняет точные schema2 records/context в native archive. Тот же gate выполняет семь exact production wrapper composition tests: state Missing/false/Error и commit до acknowledgement; config Conflict→WouldBlock с сохранением точных bytes; owner log writer/sequence и app-batch identity; committed mutation с потерянным reply без resend; неверный target до соединения; captured choice без acknowledgement с сохранением owner WAL без повторного соединения. Используются production тела owner_client/state client, настоящий owner_io framing и server Store/storage. Подставляются только host connection и peer admission. Это не подтверждает live peer authentication, физический stress 128 MiB или общую runtime readiness. Эмуляторный `InstallerCliLifecycleTest` выполняет install→uninstall→install→reboot→uninstall; разные install/uninstall сохраняются как отдельные операции для безопасного продолжения. Install monitor требует точный terminal transaction receipt CLI дополнительно к acceptance и двум независимо проверенным boot; canonical или plain terminal failure остаётся отказом даже при exit0. Независимый health по-прежнему требует contentRelation=same и runtime observation между boot fences. Четыре результата жизненного цикла публикуются только после проверки и очистки. `testFailedInstallRecovery` — явный cleanup того же run: требуются `scenario=resume`, исходные `resumeRun` и lease root `checkWorkDir`, проверенный DMG наблюдателя. Retained terminal content-identity failure и завершение runner связываются со свежим Enforcing native install-complete/two-boot proof; сохраняется `failed-reconciled` с acceptance FAILED, после чего допускается только normal uninstall до строгого nine-check receipt нового boot. Install acceptance не публикуется. Recovery использует action `--emulator-check` с `{"action":"uninstall-normal"}` отдельного host-инструмента. Он передаёт удаление публичной операции выбранного обычного установщика; внешний runner сохраняет независимые проверки отсутствия и новой загрузки. Одного exact schema-1 serial/uninstall envelope недостаточно: normal receipt должен содержать все девять независимых absence checks, новый boot проверяется независимо, status/root absence читается повторно. Ошибка admission или unknown mutation сохраняет failed acceptance и владельца без replay. Unknown cleanup сохраняет владельца без replay; отдельный старый unknown-uninstall transaction/manifest mismatch остаётся BLOCKED, uninstall transaction не угадывается. Это не подтверждение остальных UI, GUI и agent cases.

Пара `language-opposite` / `language-return` использует штатный EN/ZH picker: сохраняет исходный checked radio в журнале до изменения, выбирает противоположный язык и подтверждает подписи Voboost и свежий render-log от аттестованного endpoint именно OEM Setting. Затем исходный язык восстанавливается и проверяется так же. Архивы читаются потоково через системный tar, без распаковки имён из архива в файловую систему; expanded records удаляются после разбора, исходный архив сохраняется. После прерывания `CONFIGURE/language-cycle` read-only resolver может закрыть операцию только по свежему ActivityManager-read исходного языка в той же загрузке и здоровому текущему продукту. Это не выдаёт functional PASS прерванному сценарию. Если исходный язык не подтверждён, неизвестный исход сохраняется: переключение не повторяется и stop не разрешается.

I04 сохраняет XML всех свежих визуальных suites и все свежие actual/compare изображения до оценки ошибок. `component-results/report.json` сопоставляет выполненные suites с текущим реестром исходных visual-тестов, сверяет уникальность testcase и фактические исходы с итоговыми счётчиками, перечисляет каждый case; `index.html` открывает сравнения для вычитки. Устаревший XML, зелёный subset, пропуск, повтор case или противоречивые счётчики не дают PASS. Эталоны не меняются; отсутствующие и изменённые сравнения требуют отдельной проверки по OEM-свидетельствам владельца.

Исполнитель `none-no-processes` выбирает наблюдаемый startup radio OEM Setting, проверяет текущее описание и каноническое сохранённое поле `startup`, требует неизменности живого publisher, действующего режима, наблюдённых process lifetimes и поколений активных внедрений до перезагрузки. После своей новой загрузки он требует официальный полный bounded inventory `oem-target-processes` с явными complete/end markers и без inject, ART runtime, APK и функциональных executors. Допустим только resident owner, связанный с точным установленным daemon executable, PID/starttime и неизменным dev/inode backing с владельцем root и одной ссылкой. Успешный экспорт подписанным daemon с аутентифицированным current-session metadata ограничен двумя совпадающими наблюдениями owner; это доказательство exact installed executable, а не отдельная криптографическая аттестация процесса. Пустой legacy diagnostic header не доказывает отсутствие. Возврат использует packaged `--mode interface` только для сохранения intent следующей загрузки при неизменных owner и текущем none runtime; отдельный owned reboot предшествует независимой проверке здоровых config/runtime и вкладки Settings. Receipt выдаётся после cleanup всего lifecycle. Прерванная startup-запись закрывается read-only только в исходной загрузке при подтверждённом ожидаемом сохранённом значении; неизвестный исход не разрешает replay или shutdown. Для реализации есть host/compile evidence; новый кандидат ещё не проходил этот runtime-кейс.

Исполнитель `hidden-tbox-recovery` проверяет новую hidden-загрузку, отсутствие вкладки в полном дереве OEM Setting и текущее состояние включённых работающих targets по подписанному каталогу и полному process inventory. I03 использует закрытый выбор owning package/binary: generation recovery остаётся в package `voboost-daemon`, binary `voboost-inject`. Каждый последовательный suite обязан выдать ровно уникальные требуемые успешные результаты и одну соответствующую итоговую сводку без failed или ignored tests. После известного префикса `test NAME ... ` допустимы строгие JSON-object diagnostics и отдельный точный `ok`; diagnostics не заменяют этот результат и читаются существующим bounded JSON parser; пустой фильтр, лишние или повторные строки и противоречивые сводки не дают PASS. Host fixtures выбора и parser не заменяют выполнение owning transaction suites.

Root unitAgents выполняет существующие задачи testUnit и generateNativeRegistry перед unitInject. Owning unitInject и I05 требуют canonical непустой обычный файл `voboost-agents/build/native/registry.rs`; отсутствие generated файла даёт явный prerequisite BLOCKED с существующей командой генерации. I05 diagnostic не генерирует его автоматически. Integration environment выбирает canonical путь, не делая registry условием допуска несвязанных delivery или CLI проверок. Java fixtures подтверждают только выбор и отказ при отсутствующем prerequisite; actual owner composition остаётся отдельным host-прогоном.

Проверка режима запуска следует текущему split-контракту: resident owner сохраняет полную текущую конфигурацию через `SetStartup`, меняя только `startup` и сохраняя fence работающей загрузки. Startup receipt подтверждает durable выбор следующей загрузки, включая `none`; он не доказывает немедленное применение исполнителем и не требует остановки storage owner. Прежний desktop-контракт ожидания нового status descriptor и немедленного сброса fence удалён. Ранняя публикация injection status остаётся отдельным scheduler gate. Текущий полный projection test использует настоящие owner Store transactions и все поддерживаемые поля конфигурации; исторический root language override в эту schema не входит. Android/OEM применение и UI intent остаются независимыми runtime gates.

`voboost-agents` проверяет настоящий generated native registry задачей `testNativeRegistry`, включённой также в `testUnit` и `check`. Каждый выбранный native Codec сохраняет effective intersection логической и optional native applicability исходного Agent.json как minified JSON вместе с ID и source binding. Проверка сравнивает generated rows с выбранными original metadata; firmware identities и hash compatibility gates не добавляются. Native admission по текущим properties и отказ для неподдерживаемого chip/vehicle/Android остаются отдельными owner probe tests; один metadata projection не разрешает native execution.

I03 требует существующий inject owner CAN TX ioctl1/PID metadata policy gate до семи Rust recovery cases и до публикации acceptance. Выполняются `test-selinux-rule-generation` и `test-selinux-real-policy`, сохраняется полный log; обязательны normal и baseline C completions, policy roundtrips и unchanged-rights controls. `./gradlew testCanTxPolicy --offline` выполняет только тот же prerequisite без Cargo, DMG и I03 PASS receipt; diagnostic class исключён из обычной integration selection, чтобы не запускать C дважды. Это проверка current source-policy composition, а не policy binary внутри кандидата. Native RX/netlink, NV/property access и полная native Enforcing readiness остаются отдельными open gates.

Для очистки сохранённой неуспешной установки `testFailedInstallRecovery` принимает `-PobserverDmg=/absolute/new-installer.dmg` вместе с исходными `candidateDmg` и `resumeRun`. Оба пакета проверяются независимо. Manifest и каталог сохранённой операции остаются привязаны к исходному пакету; исполняемый файл observer выполняет чтение и штатное удаление. Эта настройка не запускает установку и не превращает неуспешный прогон в принятую установку.
