# Разработка агента

[English](agent-development.md) | **Русский**

Агент — независимый модуль одной функции. Он запускается внутри выбранного штатного процесса, проверяет доступный Java-контракт и только после этого устанавливает свои перехваты.

## Одна функция — один агент

Агент отвечает за:

- одну пользовательскую функцию
- собственный набор целевых процессов
- собственную применимость
- собственные Java-контракты
- собственную конфигурацию и состояние
- установку и снятие своих перехватов
- восстановление сохранённого исходного состояния
- документацию и тесты этой функции

Ошибка одного агента не должна останавливать другие агенты. Агент не получает конфигурацию и состояние чужих функций.

## Статусы

Исходники и выпуск beta1 содержат ровно семь stable-агентов и исполнитель ui-qinggan только для Settings. Отложенные features и их metadata находятся за пределами репозитория исходников.

## Метаданные

Каждый агент содержит `<Name>Agent.json`. Пример:

```json
{
    "id": "vehicle-drive-forced-ev",
    "category": "vehicle",
    "status": "stable",
    "order": 23,
    "class": "ru.voboost.agents.vehicle.drive.forcedev.VehicleDriveForcedEvAgent",
    "target": "com.qinggan.systemservice",
    "activation": {
        "type": "checkbox",
        "default": false
    },
    "title": {
        "en": "Forced EV mode",
        "ru": "Принудительный режим EV"
    },
    "description": {
        "en": "Keeps electric drive mode requested when the vehicle allows it.",
        "ru": "Удерживает запрос электрического режима движения, когда автомобиль его допускает."
    },
    "applicability": {
        "chip": [
            "8155"
        ],
        "vehicle": [
            "free",
            "dreamer"
        ],
        "android": [
            9,
            11
        ],
        "powertrain": [
            "hybrid"
        ],
        "market": [
            "china",
            "global"
        ]
    }
}
```

Метаданные задают:

- стабильный ID
- категорию и место в Settings
- статус
- входной класс
- точные целевые процессы
- способ включения
- локализованные название и описание
- применимость по chip, vehicle, Android, powertrain и market
- необходимые UI-ресурсы
- описание отдельной вкладки Settings, если агент её предоставляет
- конфликты и типизированные параметры, если они есть

Метаданные не содержат отдельный пакет, путь APK, сертификат, хеш штатного APK или список прошивок.

`<Name>Agent.json` проверяется до компиляции. Корень принимает только `activation`, `applicability`, `category`, `class`, `description`, `disables`, `id`, `options`, `order`, `requiresArtifacts`, `settingsTab`, `status`, `target` и `title`; неизвестные поля запрещены.

`id` — уникальное имя в kebab-case, `class` — точный FQCN входного класса, `target` — строка или непустой массив точных процессов, а локализованные строки содержат `en` и `ru`. `order` задаёт сортировку и уникальное место отображаемой записи; служебный `settings` использует отрицательное значение, а остальные показываемые агенты не могут использовать совпадающее место.

Исходники beta1 принимают только stable metadata. Каталог использует `checkbox` с булевым `default` и служебный Settings `config` с точными `key` и `value`.

Исходный валидатор metadata находится в `voboost-agents/build.gradle.kts`. Форматы создаваемого поколения задают `contracts/agent-generation/agents.schema.json`, `agent-entry-abi.json` и `README.md`. Сборка генерирует каталог и Java-реестр только из прошедших проверку metadata; ручной параллельный список агентов запрещён.

## Отдельная вкладка Settings

Агент, которому нужна отдельная вкладка в настройках машины, объявляет её в подписанных метаданных. В beta1 это делает `logs`:

```json
{
    "settingsTab": {
        "tag": "logs",
        "order": 1,
        "menuLayout": "menu_logs",
        "fragmentLayout": "fragment_logs"
    }
}
```

`tag` уникален среди выбранных агентов и не равен `voboost`. `order` задаёт положение после Voboost. Имена layout должны быть безопасными Android resource names и присутствовать во всех ABI ресурсов, заявленных агентом. Сборка переносит эти поля в подписанный каталог и проверяет XML до создания DEX.

Во время запуска агент регистрирует фабрику Fragment через `AgentContext.settingsTabs()`. Среда сама связывает регистрацию с ID агента и принятыми `settingsTab`; произвольный `ownerId`, другой тег или layout не принимаются. Агент `settings` получает только общий упорядоченный снимок реестра и не содержит специальных условий для конкретного расширения.

Регистрация не включает `settings` и не меняет `voboost-startup`. В режиме `hidden` выбранное состояние агента сохраняется, но вкладка не показывается; при возврате в `interface` активный `settings` восстанавливает её из реестра. Остановка агента обязана закрыть регистрацию и освободить контроллер содержимого.

## Целевой процесс и пакет

`target` называет точный Android process. Каталог агентов содержит только:

```json
{
    "process": "com.qinggan.systemservice",
    "boot": false
}
```

Пакет и процесс не всегда совпадают. Например, частный процесс может называться `com.qinggan.audiopolicy.service:fft`, а пакет — `com.qinggan.audiopolicy.service`. Поэтому пакет не выводится из имени процесса. Если пакет важен функции, агент проверяет его внутри Java-контракта.

## Применимость

Пять осей применимости имеют закрытые значения:

- chip: `8155`, `nxp`
- vehicle: `free`, `dreamer`
- android: `9`, `11`
- powertrain: `ev`, `hybrid`
- market: `china`, `global`

Известное несовпадение исключает агента. Неизвестное значение не превращается в угаданное: выбор остаётся неизвестным до появления достоверного факта или до runtime-проверки, если контракт допускает такой путь.

## Java-контракт

Контракт описывает доступные возможности процесса. Он может проверять:

- текущие пакет и процесс
- класс
- метод экземпляра или статический метод
- полный descriptor аргументов и результата
- modifiers
- поле и его тип
- конструктор
- службу Android
- provider и ограниченное чтение значения
- ресурс по package, type и name
- именованное статическое значение
- доверенный факт среды выполнения
- сочетания `allOf`, `anyOf` и `not`

Декларативный JSON проверяется при сборке и компилируется в неизменяемые типизированные Java-определения. Исходный JSON не загружается на устройстве и не может быть заменён локальным файлом.

Корень `<Name>Contracts.json` содержит `schemaVersion`, `feature` и непустой массив `contracts`. Вариант задаёт `id`, `bindings`, дерево `match`, `semantics`, `reads` и `actions`, когда они нужны функции.

`match` использует `allOf`, `anyOf`, `not`, `package`, `process`, `class`, `method`, `staticMethod`, `field`, `staticField`, `staticFieldValue`, `service`, `resource`, `providerValue` и `runtimeFact`. `binding` использует `class`, `constructor`, `method`, `staticMethod`, `field`, `staticField`, `staticConstant` или `staticStringConstant`. Действие и чтение ссылаются на стабильные имена `bindings`, а не выполняют второй reflection-поиск.

Проверка класса использует точный FQCN и выбранный class loader. Проверка метода использует владельца, имя только когда оно является частью устойчивого API, полный JVM descriptor, modifiers и ожидаемую статичность. Проверка поля использует владельца, устойчивое имя либо единственную структурную привязку, descriptor и modifiers. Ресурс проверяется по package, type и name; числовой ID разрешён только как результат runtime-разрешения этого имени.

Компилятор нормализует DSL, отклоняет неизвестные поля, повторяющиеся ID и bindings, пустые логические узлы, несовместимые modifiers и неоднозначные структурные привязки, затем создаёт типизированные `AgentContractDefinition` и semantic snapshot. Рабочая сборка зависит только от сгенерированных определений. Изменение DSL требует одновременного изменения схемы, компилятора, generated-catalog tests и OpenSpec.

При запуске должен совпасть ровно один полный контракт:

- ноль — `unsupported`
- один — агент может продолжить
- больше одного — `ambiguous`

`unsupported` и `ambiguous` не устанавливают перехваты и не меняют штатное состояние.

## Что нельзя использовать для выбора

- SHA штатного APK
- сертификат производителя
- номер или имя прошивки
- числовой resource ID как межпрошивочный признак
- однобуквенное имя, появившееся только после декомпиляции
- имя метода без полного descriptor
- arity вместо типов аргументов

Отдельное исключение — `font-cyrillic`: перед бинарным преобразованием он проверяет точный размер и SHA-256 файла `semibold.ttf`. Этот хеш выбирает только поддерживаемые байты шрифта, а не автомобиль, прошивку, APK или процесс.

Контракт не содержит бинарных отпечатков OEM APK, сертификатов, путей установки, названий прошивок и локальных путей к исследовательским материалам. Однобуквенное или иное обфусцированное имя не становится производственной зависимостью: допустим устойчивый публичный идентификатор либо уникальная структурная привязка, для которой zero-match и ambiguous-match безопасно завершаются без перехвата.

## Имена и расположение файлов

Код находится под `ru/voboost/agents/<feature>` и в package `ru.voboost.agents.<feature>`.

Для ID `some-like` используется полный PascalCase-префикс `SomeLike`:

```text
SomeLikeAgent.java
SomeLikeAgent.json
SomeLikeAgent.md
SomeLikeAgent.ru.md
SomeLikeContracts.json
SomeLikeContract.java
```

Каждый частный файл в каталоге агента начинается с того же префикса. Общие файлы в корне `ru.voboost.agents` начинаются с `Agent` или `Hook`.

Имена должны быть кратчайшими из однозначных. Слова, уже заданные операцией или контекстом, не повторяются.

## Тестовые заглушки

Заглушки воспроизводят только части штатного API, необходимые тестам:

- точный FQCN
- method/field descriptor
- modifiers
- constructor
- варианты наличия и отсутствия возможностей

Заглушка не входит в рабочую сборку и не доказывает наличие контракта в автомобиле. Она нужна для воспроизводимого теста уже исследованного контракта.

## Состояние

Агент не пишет SharedPreferences штатного приложения. Постоянное состояние хранит демон в `/data/voboost/state/<agent-state-key>.json`.

Через state RPC агент может:

- записать только принадлежащий ему ключ
- прочитать только принадлежащий ему ключ
- получить типизированное значение
- подтвердить изменение
- восстановить сохранённое исходное состояние после перезапуска

Файл `state/` не содержит состояние install, update, restore или uninstall.

`AgentState.set` отправляет `W|timestamp|source|key|value`, а `AgentState.get` — `R|requestId|source|key`; демон отвечает `R|requestId|status|value`. Демон выводит имя файла из source и key, проверяет владение и пределы и атомарно записывает JSON scalar. `AgentState.setConfirmed` повторяет запись ограниченное число раз и принимает успех только после точного чтения того же значения. Отдельной операции удаления state в текущем API нет.

До первого изменения агент сохраняет исходное значение и признак его наличия. Повторный запуск не перезаписывает исходное значение текущим изменённым. `stop` снимает обратные вызовы и перехваты, прекращает новые действия, дожидается уже начатых обратных вызовов в ограниченный срок, восстанавливает сохранённое значение и подтверждает восстановление контрольным чтением. Если подтвердить восстановление нельзя, данные остаются для следующей попытки, а агент сообщает `failed`.

## Жизненный цикл

```text
выбран
→ проверка контракта
→ установка перехватов
→ ожидание подтверждённой готовности
→ работа
→ запрос остановки
→ снятие перехватов и подписок
→ восстановление сохранённого исходного состояния
→ остановка
```

Если запуск завершается ошибкой, агент сначала прекращает менять штатное поведение и выполняет доступную очистку. Только после этого он публикует `failed`.

Установка выполняется транзакционно: выбрать единственный контракт, получить привязки, прочитать исходное состояние, подготовить и установить перехваты, выполнить разрешённое действие, дождаться ACK, сделать независимое readback и опубликовать readiness. Ошибка на любом шаге откатывает только уже выполненные шаги в обратном порядке. Обратный вызов после запроса остановки, смены эпохи или закрытия поколения отбрасывается проверкой актуальности.

## Диагностика

Агент использует свой точный ID как источник и метку лога. Каждый существенный шаг пишет структурированную запись:

- проверяемый предикат
- фактический результат
- ожидаемое значение
- причина `MATCH`, `NO_MATCH`, `SKIPPED`, `PENDING` или ошибки
- установка и снятие перехвата
- действие и контрольное чтение
- сохранение и восстановление состояния

Эти записи идут по единому транспорту к демону. Агент не пишет logcat или файлы штатного процесса.

Запись содержит `agentId`, поколение, процесс, PID/starttime, эпоху, уровень `debug`, `info` или `error`, стабильный event ID, результат, ожидаемое и фактическое значения без секретов. Полные stack trace, пользовательские данные и произвольный `toString()` штатных объектов не отправляются. Транспорт описан в [логах](logs.ru.md).

## Документация и OpenSpec

Каждый агент имеет:

- `<Name>Agent.ru.md`
- `<Name>Agent.md`
- собственную capability `openspec/specs/agent-<exact-id>/spec.md`
- именованные Gate для проверяемых сценариев
- `Unverified` для наблюдений, которые требуют другой среды

Документы агента объясняют назначение, применимость, контракт, действия, состояние, остановку, доказательства и оставшиеся ограничения. Русская и английская версии совпадают по структуре и утверждениям.

Исходники среды находятся в `voboost-agents/src/main/java/ru/voboost/agents`, код и метаданные функции — в её подпакете, host-тесты — в `voboost-agents/src/test/java/ru/voboost/agents`, заглушки — в `voboost-agents/stubs`, capabilities — в `voboost-agents/openspec/specs`. Проверяемые требования получают именованные Gate; исследованное, но не доказанное в требуемой среде, остаётся `Unverified` и не повышает статус агента.

Основная проверка:

```bash
./gradlew check buildRelease
npm run openspec:validate
npm run docs:check
```
