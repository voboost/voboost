# Offline installer

[English](installer.md) | **Русский**

`voboost-installer` предоставляет один Rust operation core для Tauri GUI и CLI. Он получает один immutable signed product closure из `voboost/release`; в runtime нет выбора выпуска, download артефактов, переключения channel и component build.

## Startup routing

До Welcome установщик выполняет ограниченную проверку машины. Активная операция открывает Current Operation. Исправно установленный продукт открывает management actions. Recoverable degraded state предлагает Restore и Uninstall. Unknown или unrecoverable state запрещает mutation и показывает точную диагностику. Только отсутствие продукта открывает installation flow.

Installed management предлагает startup mode, Restore, logs, Uninstall и Upgrade, только когда выпуск внутри установщика новее и compatibility разрешает переход. Установщик не управляет отдельными агентами и не предлагает downgrade.

Переключатель запуска сохраняет выбор для следующей загрузки машины. Каноническая квитанция подтверждает запись конфигурации на диск, а не немедленную активацию runtime. Текущая загрузка сохраняет свой прежний режим; запись не перезапускает inject и не ждёт его статуса. Демон хранилища остаётся работающим и при выбранном режиме `none`.

## Типизированная граница

WebView передаёт только проверенный ADB serial, закрытый enum operation или startup mode `interface`, `hidden`, `none`. Он не передаёт shell fragment, executable, device path, manifest path и произвольный argument. Device operations используют фиксированные endpoints `voboost-daemon` и canonical receipts.

## Offline packages

| Платформа | Пакет | Product/ADB storage |
| --- | --- | --- |
| Windows 10/11 x86-64 | `voboost-installer-<release>.exe` | product closure и официальный ADB trio встроены в один portable PE |
| macOS arm64+x86_64 | `voboost-installer-<release>.dmg` | отдельные arm64/x86_64 приложения, связанный прямой ADB, один flat closure в Resources, CLI symlink |
| Linux x86-64 | `voboost-installer-<release>.tar.bz2` | одна CLI-only ELF entry с mode `0755` и встроенным closure; системный ADB из фиксированных защищённых путей backend |

В macOS DMG нет архивов и деревьев исходников. Packager проверяет отдельную поставку `corresponding-source.tar.gz`, `corresponding-source.json`, `BUILD-MODIFIED.md`, но не экспортирует её рядом с DMG; локальный builder сохраняет её в рабочем каталоге. Читаемые лицензии остаются в приложении. См. [модифицированную сборку](build-modified.ru.md).

Windows GUI требует заранее установленный совместимый WebView2 Runtime. Установщик не включает, не скачивает и не устанавливает WebView2. CLI arguments разбираются до GUI initialization и работают без WebView2.

## Artifact source

Common core читает package bytes через один закрытый `ArtifactSource`: точный список, bounded streaming open и declared identity из `voboost.json`. Он отклоняет duplicate names, overlap, out-of-bounds data, unsupported compression, undeclared trailing bytes и любое несовпадение actual size/SHA-256.

## Работа с версиями

Установщик продолжает любую активную операцию до Welcome или EULA независимо от версии, которая её начала. Restore и Uninstall используют установленную authority машины. Upgrade использует комплект внутри запущенного установщика и появляется, только если его выпуск строго новее, а compatibility разрешает переход. Более старый установщик не предлагает downgrade. При неизвестной схеме доступны только ограниченная диагностика, Retry и logs, если подтверждён фиксированный endpoint.

## Реализация и разработка компонента

`voboost-installer` — полностью офлайн-программа с графическим интерфейсом и командной строкой для установки Voboost, управления установленным выпуском, восстановления после штатной прошивки, выгрузки логов и полного удаления через USB.

GUI связывает асинхронные результаты с подключённым устройством и эпохой операции. Отключение, сброс и повторное монтирование отменяют старые результаты, включая повторное подключение с тем же serial. Черновик режима управления принадлежит одной сессии устройства; неизменённый черновик следует последнему подтверждённому режиму.

### Запуск

Без аргументов открывается графический интерфейс. Для командной строки доступны:

```text
voboost-installer --install [--device SERIAL]
voboost-installer --restore [--device SERIAL]
voboost-installer --logs DIRECTORY [--device SERIAL]
voboost-installer --uninstall [--device SERIAL]
```

Основной исполняемый файл из пакета также принимает `voboost-installer --device SERIAL` без консольной операции и открывает GUI для ровно этой цели. Он использует парсер устройства CLI и сохраняет цель при обнаружении устройств, операциях, запуске дочерних helpers и переподключении. Недоступное выбранное устройство не подменяется другим. Без `--device` сохраняется прежнее обнаружение по умолчанию.

Перед штатным удалением установщик сохраняет проверенную идентичность pristine policy. После перезагрузки, выполненной root-компонентом, boot inputs штатного init могут доказать удаление policy при permission denial чтения loaded policy. Все девять проверок отсутствия остаются обязательными; эта верификация сохраняет SELinux Enforcing.

Если при удалении пропала связь с приборкой, повторите `--uninstall` на той же машине. Установщик сверит сохранённую транзакцию и подготовленный финализатор. Для завершения нужны подписанная квитанция QNX и внешние проверки отсутствия Voboost в Android.

При ошибке штатного удаления существующий диагностический отчёт показывает контекст SELinux, режим enforcement и метаданные двух фиксированных policy, а также статус и ограниченный текст ошибки одной попытки чтения. Наличие или отсутствие маркеров выводится только после успешного полного чтения; эти read-only сведения не заменяют доказательство отсутствия Voboost.

Установка не показывает обязательный экран лицензии и не запрашивает согласие. Тексты лицензий и уведомления о сторонних компонентах остаются в поставке.

Во всех трёх сборках CLI также поддерживает `--status` и `--mode interface|hidden|none`; в Windows и macOS те же действия доступны на графическом экране управления. В Windows и macOS флаг `--dry-run` вместе с консольной операцией проверяет её аргументы без запуска графического runtime, поиска ADB, подключения к машине и записи логов; Install дополнительно проверяет встроенный подписанный комплект продукта.

До Welcome установщик проверяет подключённую машину. Активная операция сразу продолжается; для установленного продукта открывается экран управления с режимом запуска, Restore, логами, Uninstall и Upgrade, только если встроенный выпуск новее и совместим.

`voboost-installer-1.0.0-beta1.exe` — один portable-файл для Windows x86-64. Для графического интерфейса нужен Microsoft Edge WebView2 Runtime, а команды CLI работают без WebView2. Установщик извлекает во временный закрытый каталог только `adb.exe`, `AdbWinApi.dll` и `AdbWinUsbApi.dll`.

`voboost-installer-1.0.0-beta1-arm64.dmg` и `voboost-installer-1.0.0-beta1-x86_64.dmg` содержат `Voboost Installer.app` соответствующей архитектуры и корневую ссылку `voboost-installer` на тот же executable. macOS использует встроенный прямой ADB без внешнего executable ADB. `voboost-installer-1.0.0-beta1.tar.bz2` содержит Linux x86-64 CLI с mode `0755` и закреплённые лицензии и уведомления; Linux выбирает системный ADB из фиксированных защищённых путей.

Упаковщик проверяет соответствующие исходники как внутренний вход сборки; отдельный архив рядом с DMG не создаётся. Файлы `corresponding-source.tar.gz`, `corresponding-source.json` и `BUILD-MODIFIED.md` не входят в образ и приложение.

Установка и Restore выполняют только те перезагрузки мультимедиа, которые нужны текущей проверенной фазе. Uninstall завершается после внешней проверки отсутствия Voboost.

На всех поддерживаемых платформах CLI умеет устанавливать, обновлять, восстанавливать и удалять продукт, показывать статус и справку, менять режим запуска, сохранять логи и проверять пакет. Команда `--update` применяет встроенный проверенный выпуск к установленному продукту и сохраняет его настройки. Обновление можно запустить и из установленного приложения. Windows и macOS также поддерживают `--dry-run`, `--diagnostics` и `--emulator-check`. Команда `--licenses` доступна в Windows. Проверки работы на устройстве фиксируются отдельно для каждой платформы.

`--observe --device SERIAL` читает фиксированные сохранённые файлы, не меняя состояние гостя. Native backend macOS и отдельный Linux CLI используют единый предел закодированного ответа и парсера: 100 MiB (104 857 600 байт), включая HEX и служебные поля. При превышении возвращается `unavailable`; усечённый ответ не принимается. Декодированная runtime-публикация ограничена 1 MiB согласно контракту её владельца, остальные фиксированные файлы сохраняют предел 32 KiB. Для stderr Observe и обычных текстовых команд остаются отдельные пределы 64 KiB. Эти ограничения не доказывают готовность runtime или автомобиля.

`--observe-native-can CURSOR --device SERIAL` — закрытое диагностическое чтение в desktop и отдельном Linux CLI. CURSOR — каноническое беззнаковое десятичное число размером 64 бита. На явно выбранном устройстве выполняется только `/data/voboost/voboost-daemon --observe-native-can CURSOR` с ограниченным общим временем ожидания и чтения. Команда не подготавливает root, не устанавливает продукт, не перезагружает устройство, не меняет SELinux и не принимает shell-аргументы. Демон проверяет владельца и выдаёт диагностическую аренду приёмника на пятнадцать секунд. Она позволяет читать исходные кадры при выключенных агентах, не включая их политику и не отправляя CAN-команды.

Страница фактического приёма из ядра содержит эпохи загрузки, writer и receiver, непрерывные номера исходных записей, признаки потерь и ошибок и временную границу последнего EAGAIN. `active` означает, что очередь приёма прочитана до этой границы; unavailable, draining, разрыв cursor, устаревшая граница или смена эпохи не доказывают непрерывное покрытие. Счётчик policy `discarded` отличается от пропущенных исходных записей. Граница холодного запуска требует отдельного доказательства закрытой ECU-модели; новое выборочное чтение состояния её не заменяет. Host-тесты CLI и парсера проверяют транспорт; приёмка упакованной сборки в runtime остаётся отдельной обязательной проверкой.

### Разработка

```text
npm ci
npm run typecheck
npm run lint:check
npm run format:check
npm test -- --run
npm run test:build
npm run build
./scripts/cargo-test-with-ephemeral-role-roots.sh
```

Rust test helper получает `VOBOOST_PRODUCT_VERSION` из product-owned wire fixture `installed-healthy.json`, игнорируя унаследованную версию выпуска. Он создаёт одноразовые тестовые корни ролей и восстанавливает исходное дерево `resources-staged` после успеха, ошибки или сигнала. Эта identity нужна только host-проверкам; production packaging по-прежнему требует замороженных version inputs из product build chain.

Подробные контракты находятся в [`voboost/docs-dev`](), пользовательские инструкции — в [`voboost/docs-user`](../docs-user).

Адаптер проверки в эмуляторе запускается через `--emulator-check /absolute/request.json --device emulator-PORT`. Он принимает только закрытые действия интерфейса, перезагрузки, диагностики и заранее проверенного тестового APK, проверяет QEMU и Enforcing до получения root и не принимает команды shell или аргументы ADB. Функциональная проверка использует упакованный CLI установщика для всех операций на устройстве и CLI Voyemu для управления профилем; её результат не подтверждает работоспособность в физическом автомобиле.

Закрытые действия `inspect`, `snapshot` и `screenshot` могут наблюдать активную установку через уже работающий root-доступ в Enforcing, не подготавливая root и не захватывая блокировку установки. `inspect` сообщает о завершении загрузки; фиксированные клавиши `sleep` и `wake` позволяют проверить переход питания в эмуляторе. Эти наблюдения не подтверждают поведение ACC физической машины.

Закрытое действие `fault-window` проверяет реальный отказ изменения startup, потерю ответа чтения vehicle state или однократный обрыв авторизованного запроса удаления в том же установленном комплекте. Нужны уже работающий root, QEMU, Enforcing и точные boot, manifest, generation, catalog и PID/starttime цели. Во время обычных UI-действий через packaged CLI его stdin pipe остаётся открытым: первая JSON-квитанция сообщает `armed`, а закрытие stdin приводит к соответствующей квитанции `closed` после уборки. Native-владелец завершает окно через девяносто секунд; смерть владельца делает маркер неактивным. Квитанции определяют диагностическое окно, а результат проверки требует реальных наблюдений Java, демона и видимого интерфейса. См. [native-контракт](../../voboost-inject/openspec/specs/emulator-diagnostics/spec.md).

Аварийное CLI-удаление также восстанавливает исходные SHA selectors init до удаления recovery-данных. Оно читает только фиксированную root-owned authority, проверяет полный набор Android 9/11, повторно сверяет байты после остановки служб и сохраняет recovery при подмене или symlink. Неполный backup selectors считается ошибкой, а не успешным удалением.

Первоначальная установка выполняет adb root, adb remount и проверенный setenforce 0. Установщик восстанавливает Enforcing; native-установка после reboot проверяет Enforcing и отвергает Permissive. Исключение действует для первоначальной подготовки и Retry до первого reboot, а не для дальнейшей работы агентов.

### Тексты лицензий в пакетах релиза

Канонические английская и русская лицензии Voboost и оригинальные уведомления поставляемых компонентов находятся в `Voboost Installer.app/Contents/Resources` на macOS и рядом с распакованным исполняемым файлом Linux. Пункт **Лицензии…** в меню приложения macOS или меню Help Windows открывает отдельное окно с группами компонентов, полными условиями и поиском по документу. Просмотр читает уведомления из пакета без принятия условий установки и обращения к автомобилю. В Windows команда `voboost-installer-1.0.0-beta1.exe --licenses C:\absolute\new-directory` проверяет встроенный пакет и сохраняет точный комплект лицензий в новый каталог без ADB и открытия GUI. Android APK содержит общие уведомления продукта в `assets/licenses/`. Условия сторонних компонентов сохраняются отдельно от лицензии Voboost. GUI показывает MIT отдельно от разрешения собственника на установку и предупреждения о рисках.

Транзакции файлов защищённых ресурсов фиксируют точную идентичность блочного устройства и исходный флаг read-only до устойчивой записи журнала remount. Для ext4/f2fs переход в writable использует общий механизм protected-block. Штатное завершение и watchdog сначала возвращают файловую систему в read-only, затем восстанавливают исходный флаг блочного устройства. Восстановление сверяет сохранённый журнал с унаследованными транзакцией, целью, топологией монтирования и исходными флагами; неполные полномочия или ошибка восстановления сохраняют журнал и блокируют дальнейшую запись. Журнал требует актуальную схему и явные исходные флаги; после прерванного снятия защиты её исходное состояние не угадывается по текущему устройству.

Прерванное обновление продолжается с сохранённым идентификатором, если его защищённый журнал указывает на тот же проверенный комплект, в том числе при `--install --force`. Продолжение наблюдает существующую операцию вместо повторной передачи файлов. Ошибка системного шага публикуется как неуспешная операция с причиной; журнал восстановления сохраняется, а состояние не должно бесконечно оставаться running.
