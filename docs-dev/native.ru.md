# Native runtime

[English](native.md) | **Русский**

Native runtime находится в [`voboost-inject`](../../voboost-inject). Cargo package `voboost-daemon` собирает две постоянные программы: `voboost-daemon` владеет runtime-состоянием, конфигурацией и файловыми логами; `voboost-inject` — допуском агентов и внедрением. Разделённое исходное дерево ещё требует нового подписанного выпуска и runtime-приёмки.

## Границы исходников

В репозитории остаются `daemon/`, `injector/`, `implant/`, `install/`, `restore/`, `uninstall/`, `selinux/` и `shared/`. Общие привилегированные wire/storage types и проверка APK identity находятся в плоских модулях [`contract`](../../voboost-inject/contract). Java runtime отдельно принадлежит [`voboost-agents`](../../voboost-agents/src/main/java/ru/voboost/agents).

## Допуск процесса и внедрение

`voboost-inject` допускает процесс только после проверки стабильных PID/start time, точного `argv[0]`, UID, SELinux context, executable и ABI. C-инжектор повторяет identity после остановки thread group, единолично владеет временным состоянием ptrace, восстанавливает registers/signals при каждом отказе и загружает implant только точного ABI.

Выпуск использует плоские versionless имена `libimplant-arm64-v8a.so` и `libimplant-armeabi-v7a.so`. Каждая библиотека статически включает LSPlant и dex_builder с одной копией статического C++ runtime.

## Bootstrap и время жизни

`voboost-inject` открывает проверенные файлы generation через удерживаемые дескрипторы и передаёт `agent-common.dex` и только target-specific module DEX. Implant ограничивает bootstrap envelope, создаёт sealed memory-backed files, подключается к ART, подготавливает LSPlant и запускает `AgentEntry`.

Успешный `dlopen` не означает readiness. Java acknowledgement связывает generation, process start time, target и connection epoch. При stop приём callbacks закрывается до снятия hooks и освобождения JNI resources. Загруженный код может оставаться до завершения OEM process, но после cleanup не остаётся активных hooks и владельцев транспорта.

## Root authority

`voboost-daemon` владеет постоянной runtime-конфигурацией, состоянием агентов и файловыми логами через закрытый аутентифицированный протокол. `voboost-inject` владеет применимостью, публикацией поколений и допуском обновлений. Приложение передаёт недоверенные candidate bytes; установщик передаёт packaged closure и наблюдает typed operations. Ни один из них не исполняет произвольный native path и не выбирает native roles.

## Нативная часть vehicle-агентов

Rust-кодеки принадлежат своим агентам, лежат рядом с Java-кодом и объявлены через `native.source`. Gradle генерирует выбранный native registry до сборки daemon. Владелец кеширует включённые части после надёжной записи конфигурации. Обычная смена режима запуска действует со следующей загрузки; исключение — явный жест восстановления скрытого интерфейса. При каждом native poll не перечитываются конфигурация агентов или история логов. При запуске владелец создаёт новую сессию записи логов без чтения истории.

Владелец читает CAN через ограниченный protocol21 netlink с проверкой kernel sender, группы, кадра и truncation. При выключении части её samples удаляются; ошибка транспорта очищает samples, одинаковые повторные ожидания не повторяют события лога. Samples — наблюдения приёма, а не выбор пользователя или доказательство свежести ECU.

До запуска `CanBusService` владелец может отправить закодированную агентом команду через ранний native ioctl при выполнении проверок допуска и входных данных. После обнаружения сервиса raw backend отключается на весь срок жизни daemon. Последующие команды идут через аутентифицированную семантическую очередь, inject и тонкий Java-транспорт, вызывающий OEM setter; Java не владеет политикой функций, а при недоступном endpoint возврата к raw backend нет. Принятый вызов setter не доказывает применение ECU; свежие наблюдения CAN RX служат отдельным свидетельством.

Эта реализация в исходниках требует нового подписанного выпуска и runtime-приёмки. В Voyemu отсутствует новый native CAN driver; права RX, NV и properties, работа SELinux во время выполнения и физическое время 3–5 секунд ещё не приняты.

Декодеры агентов возвращают именованные скалярные поля. Демон хранит samples по источнику и полю, поэтому состояние Forced EV и режим движения не перезаписывают друг друга. Debug-события указывают поле и его OEM-значение; повтор того же значения обновляет время приёма без повторного события изменения.

Установщик определяет постоянные аппаратные сведения до публикации init-службы. При обычной загрузке демон читает существующий доверенный `vehicle.json` и не открывает NVRAM. Допуск нативной части сверяет сохранённые сведения с текущими признаками платформы; отсутствие, повреждение, противоречие или несовпадение оставляют Forced EV недоступным. `--recompute-profile` явно обновляет сведения для диагностики. Существующий выбор DEX использует доверенный установленный профиль; проверка нативного кеша не определяет уникальную машину и не доказывает общую защиту от копирования профиля.

## Consumer product manifest

Закрытый native parser проверяет `voboost.json`, его подпись, compatibility, полный inventory, APK identity, соответствие каталогу агентов и size/SHA-256 артефактов. Первичная установка, runtime injection, OTA activation, Restore и active native status используют одну product authority. Native host-gates покрывают Cargo/C/C++ tests, ptrace rollback fixtures, объединение contract, переименование binary, role signatures, product-candidate activation, компиляцию SELinux policy и Android cross-build. Physical device injection, runtime SELinux Enforcing и поведение в автомобиле остаются отдельными gates.

## Реализация и разработка компонента

`voboost-inject` — системная часть Voboost для Android 9 и 11. Репозиторий содержит root-демон, native-инжектор, внутрипроцессный implant, системные программы `voboost-install`, `voboost-restore`, `voboost-uninstall` и `voboost-selinux`, а также политику SELinux.

Реализация следует архитектуре и требованиям этой документации и применённых OpenSpec.

### Компоненты

- `daemon/` — собирает две постоянные программы: `voboost-daemon` владеет runtime-конфигурацией, состоянием и файловыми логами; `voboost-inject` проверяет входы агентов, управляет поколениями, выбирает допустимые процессы и запускает внедрение
- `injector/` — выполняет ограниченную ptrace-транзакцию, загружает implant и восстанавливает состояние целевого процесса при успехе, ошибке или прерывании
- `implant/` — подключается к ART, загружает DEX из переданных дескрипторов, инициализирует LSPlant и обслуживает runtime-каналы агентов
- `install/` — продолжает подписанную установку на устройстве и записывает проверяемый результат операции
- `restore/` — принимает текущее штатное состояние после обновления прошивки как новый baseline и повторно применяет разрешённые изменения Voboost
- `uninstall/` — останавливает Voboost, восстанавливает baseline, удаляет принадлежащие Voboost объекты и доказывает их отсутствие
- `selinux/` — содержит политику и системную программу для фиксированных изменений политики и меток
- `contract/` — плоский crate `voboost-contract` для APK identity, operation, install/generation, canonical product-release и app/daemon status contracts; `shared/` содержит implementation helpers, которые не входят в этот публичный контракт
- `openspec/specs/` — применённые требования native runtime и системных операций
- `test/` и `tools/` — host-тесты, contract checks и release tooling

### Границы ответственности

Порядок захваченных действий для native-агентов определяет daemon, а не клиент внедрения. Закрытый prepare проверяет объявленные source/key, загрузку и идентичность действия, устойчиво пишет pending до native admission и различает конфликтующие и вытесненные действия. Finish требует точного последнего identity и того же значения canonical option перед очисткой pending. Generic замена журнала не может менять зарегистрированный журнал захваченного выбора. Inject сохраняет проверку endpoint и catalog option и передаёт типизированные запросы без локального сохранения или автоматического повтора после потерянного ответа. Host composition проверяет сохранение prepare/finish при потере ответа; это не доказывает отмену CAN-команды или применение на машине.

При неопределённом результате journal I/O демон удерживает последнее неподтверждённое действие и сохраняет запрет для его источника при изменении других настроек. Эта запись в памяти не доказывает устойчивость после замены процесса daemon. Восстановление владельца продолжает его сохранённое действие прежде старого WAL; конфликтующий duplicate не может заменить известный устойчивый identity.

Закрытый протокол владельца при каждом подключении проверяет root credentials peer, точный путь executable и доверенные метаданные файла. Каждый процесс удерживает не более одного успешно проверенного executable-дескриптора для каждой роли daemon и inject. При неизменной идентичности дескриптора результат Ed25519 используется без повторного чтения бинарника; замена или изменение inode, размера, числа ссылок, владельца, прав, времени изменения содержимого или метаданных требует новой проверки. Кеш удерживает открытый дескриптор, повторно сверяет текущий executable процесса, существует только в памяти и не хранит хеши совместимости прошивок. Cache hit подтверждает executable, но не достоверность данных автомобиля или право отправить CAN-команду.

Ни одна постоянная программа не скачивает обновления и не выбирает пользовательские функции. Android-приложение подготавливает недоверенное предложение, а `voboost-inject` проверяет подписи, закрытые схемы, полный состав и допустимость процесса до публикации поколения и внедрения. Изменения постоянного runtime-состояния он запрашивает через аутентифицированный протокол владельца.

`voboost-inject` сохраняет один синхронный управляющий цикл и запускает блокирующие jobs внедрения/rebind для всех доступных разных PID в порядке startupPriority из каталога. Свежие цели и повторы используют общую очередь; при равном приоритете повтор допускается первым. У каждого PID один владелец полного bootstrap, который передаёт все применимые модули процесса. Только управляющий цикл принимает дескрипторы результата, согласует актуальное desired state и публикует статус через владельца. Остановка, удаление и native update handoff дожидаются завершения активных jobs; результат старого поколения сохраняет управляемый endpoint под исходной resident authority.

Injector не выбирает PID или Java-контракт, implant не читает постоянные файлы Voboost, а агенты не получают root. Установка, восстановление, удаление и изменение SELinux выполняются отдельными системными программами с закрытыми сценариями.

[Контракт диагностики эмулятора](../../voboost-inject/openspec/specs/emulator-diagnostics/spec.md) допускает три ограниченных операторских окна только через точный установленный подписанный демон на QEMU в Enforcing. Окно удерживает реальную mutation lock, теряет только авторизованные ответы чтения фиксированных state keys либо один авторизованный транспорт запроса удаления из Settings до долговечного принятия. Оно не подменяет сохранённое состояние или runtime status. Упакованный установщик держит владельца через отдельную stdin pipe; EOF, срок окна и проверка живого владельца прекращают эффект. Host-проверки покрывают закрытый протокол и производственную маршрутизацию; реальные JNI retry/cancel и тексты ошибок Settings требуют цикла в эмуляторе на том же подписанном комплекте.

Beta1 использует отдельные роли доверия для Android APK, product manifest, каталога агентов, разрешения восстановления и native executables. У `voboost.json`, `agents.json` и `restore.json` разные authority. Роль native executable подписывает ELF с обязательной привязкой к `daemon`, `inject`, `install`, `restore`, `uninstall` или `selinux`; программа SELinux принимается только с `role=selinux`.

На устройстве нет изменяемого хранилища ключей и смены ключей во время работы. Публичные ключи встроены в проверяющие компоненты, а смена ключа выполняется согласованным выпуском или установкой с компьютера.

`contract/release.rs` реализует product-owned schema `voboost.json` и проверяет общий adversarial corpus без импорта исходников product repository. Первичная установка использует этот подписанный манифест, один плоский набор `voboost-app.apk`, native artifacts и агентов и связанный с manifest `staging.json`; первое поколение агентов вычисляется из принадлежащих демону фактов о машине без receipt от приложения. Runtime injection, OTA activation, Restore и active native status используют одну подписанную product authority. `contract/status.rs` задаёт channel-independent wire для proposal, active identity, результата и descriptor handoff.

Установка, восстановление и удаление запрашивают только те перезагрузки, которые нужны текущей проверенной фазе. Число перезагрузок удаления заранее не фиксируется: операция завершается после terminal cleanup и доказанного отсутствия Voboost.

Native-удаление сохраняет в журнале исходный read-only флаг блочного устройства каждого проверенного защищённого mount, снимает его перед записью и восстанавливает после RO remount. Worker init ограниченно ждёт передачи lease от daemon, который запустил удаление. Оба пути сохраняют SELinux Enforcing.

Remote call отделяет исход транспортной операции от результата функции. Ошибка блокирует дальнейшие вызовы в target process и сообщает этап и исход восстановления регистров. Одно восстановление регистров не доказывает безопасность продолжения ART managed stack; причина падения Launcher при stack walk остаётся предметом исследования.

Необязательная диагностика этапов LSPlant отмечает границы DEX/JNI, конструкторов GC critical и SuspendAll, а также окончания mutation. Она использует обычный канал записей с trylock/drop; отсутствие marker означает недоступное наблюдение и не определяет ART lock или недостигнутый этап.

Для точной managed bootstrap load фазы native loader/dlsym сохраняют guard всей группы потоков. Затем injector отключает execution clone tracing и освобождает peers перед ART initialization, сохраняя восстановление и cleanup ownership execution TID. Ошибка входа прекращает initialization; новые untraced workers не становятся owned задачами managed cleanup. Target scheduling и managed continuation по-прежнему требуют runtime проверки.

Remote diagnostics различают исходные сохранённые PC/LR с признаком доступности и PC/LR остановленного callee, используя фиксированные native/managed-init/handoff phase labels. Поля копируются из уже захваченных регистров; они не определяют lock owner, прямой caller или безопасность продолжения ART.

При non-return signal stop bounded callee diagnostics выполняются до восстановления исходного контекста. ARM64 читает не более шестнадцати saved FP/LR pairs в точном стеке остановленного execution TID и сообщает только адреса и доступность. Partial, invalid и unavailable chain не считаются полным unwind; неподтверждённый ARM32 layout остаётся unavailable. Signal delivery и restoration policy не изменены.

Production hook bridge требует per-hook LSPlant publication extension. Он публикует настоящий reflected Java backup до target entry activation и вне SuspendAll; отказ publication прекращает activation. Java afterreturn setter остаётся идемпотентным. Runtime OFF/ON acceptance проверяется отдельно.

### Epoch владельца Cluster

Android authority epoch для QNX mailbox принадлежит постоянному `voboost-daemon`. Inject получает его через подтверждённый закрытый протокол владельца и не создаёт или кеширует собственную замену. Поэтому перезапуск inject сохраняет QNX owner epoch, а замена демона хранилища создаёт новый и отменяет наблюдения и delivery leases предыдущего владельца. Если владелец недоступен, операция отклоняется без локального fallback epoch. Эта идентичность отделена от logging writer ID и не требует чтения истории логов.

Чтение и сохранение состояния mailbox проходят через закрытый протокол владельца. Владелец проверяет полную каноническую схему документа и атомарно заменяет фиксированный приватный файл `cluster/mailbox.json`, только если его байты совпадают с ожидаемыми. Inject удерживает блокировку транзакции Cluster во время запроса; владелец повторно её не захватывает. Недоступность владельца или конфликт документа прекращают операцию без локальной записи и повторной отправки изменения.

Подписанные запросы, квитанции и отчёты удаления также записывает daemon. Протокол выбирает фиксированную роль документа, а не переданный вызывающим процессом путь. Перед записью daemon проверяет парную подпись; квитанции и отчёты восстановления должны соответствовать сохранённому ожидающему запросу. Небезопасные существующие файлы назначения отклоняются.

При импорте pairing аутентифицированный inject передаёт владельцу защищённые входы с ограничением размера. Inject сохраняет проверки отделения от ключей выпуска; владелец проверяет канонический provision, соответствующий ему signing seed и идентичность credentials перед записью фиксированных приватных файлов. Provision публикуется последним; совпадающий прерванный импорт можно завершить, а точный повтор завершённого импорта не пишет файлы. Отсутствующий mailbox при существующем provision считается ошибкой, а не разрешением заново создать authority. Сам транспорт courier ещё требует переноса владения.

### Разработка

Требуются Rust из `rust-toolchain.toml`, Node.js `24.13.0`, npm, Android NDK `29.0.14206865`, `cargo-ndk` 4.1.2, OpenSSL и `uncrustify`. Задайте `NDK_HOME` на полную общую upstream-установку NDK вне рабочих деревьев проектов. Make передаёт тот же путь в `ANDROID_NDK_HOME` для `cargo-ndk` и не скачивает NDK. Продуктовая сборка получает этот путь через явный параметр `androidNdkHome`.

Для стандартного расположения SDK на macOS:

```bash
export NDK_HOME="$HOME/Library/Android/sdk/ndk/29.0.14206865"
make check-ndk
```

Voboost и Voyemu могут использовать одну установку. Удаление или пересборка любого рабочего дерева не должны удалять общий NDK. Сохраняйте штатные host helpers, включая Python-скрипты, которые внутренне использует `ndk-build`.

Подготовка checkout:

```bash
make init
make check
```

Полные host-gates:

```bash
make lint
make test
make build
```

Development-сборка Android со временными ключами всех native-ролей:

```bash
npm ci
npm run dev:android
```

Проверка OpenSpec отдельно от остальных gates:

```bash
npm run check:openspec
```

`make build` собирает host release-профиль демона и не подтверждает Android, ptrace, init или SELinux Enforcing. `npm run dev:android` собирает Android-компоненты для разработки, но не доказывает установку и работу на устройстве или в автомобиле.

После canonical Android build команда `tools/prepare-beta1-unsigned.sh <output-dir>` экспортирует ровно десять плоских неподписанных native inputs для product beta1 composition. Она проверяет ABI, ELF hardening, отсутствие debug sections и host paths, не читает signing secrets и ничего не публикует.

Native source preparation использует pinned build copies в `build/third-party-source/`. Live submodules остаются неизменными; неожиданный drift копии или исходников блокирует компиляцию.

Первоначальная подготовка выполняет adb root, adb remount и проверенный setenforce 0. Установщик восстанавливает Enforcing; установка после reboot проверяет Enforcing и отвергает Permissive. Исключение действует для первоначальной подготовки и Retry до первого reboot. Desktop bootstrap и native SELinux helper получают штатный контекст исполнения shell при создании в приватном временном каталоге, затем сохраняют тот же inode на фиксированных root-owned путях. Подписи, байты и права проверяются до запуска; контексты Voboost применяет существующий сервис relabel при первой загрузке.

Если штатный root-домен не может прочитать загруженную policy при первоначальной установке, подписанный helper восстанавливает исходный источник загрузки по совпадающим sidecar-файлам прошивки либо по фиксированным снимкам CIL через штатный компилятор. Выбор источника Android 9 и 11 ограничен и сохраняет дополнительные части policy; неподдерживаемые форматы и опасные входы отклоняются. Host fixtures проверяют выбор источника и очистку дочернего процесса; фактическая установка остаётся отдельной target-проверкой.

Откат политики включает исходные SHA selectors init (один на Android 9, три на Android 11), включая исходное отсутствие файла. Metadata политики schema-v2 и terminal recovery сохраняют selectors до проверки точного восстановления. Наличие приоритетной ODM policy отвергается текущим контрактом публикации только vendor. Host-проверки не доказывают права первоначального stock root на публикацию и target acceptance.

В событии `storage endpoint available` owner записывает `processStartedBootMs` и `endpointReadyBootMs` по Linux `CLOCK_BOOTTIME`, а `startupDurationMs` — по монотонным часам процесса после инициализации хранилища и native-конфигурации. Недоступные или некорректные часы обозначаются полем `bootClockUnavailable`, а не нулём. Эти отметки измеряют готовность owner от загрузки ядра, но не применение ECU и не физическое начало пробуждения машины.
