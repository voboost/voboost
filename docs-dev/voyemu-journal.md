# Voyemu dispatch reservation journal

The host-side journal is an isolated, fail-closed building block. `VoyemuClient.lookupReserved` can construct a read-only lookup after matching the reservation against the exact original request bytes, request ID, derived scope, and the caller-supplied identity label. Mutation dispatch remains blocked. The journal cannot establish machine identity, scope, or their relationship to request bytes; its caller must establish these independently before any future integration.

A trusted local directory must be dedicated to the entire mutation domain. Every cooperating process must use the same directory and lock inode, and permissions must prevent replacement, deletion, symlinks, or external writes. The journal's protection does not cover other directories, hosts, noncooperating processes, or unreliable filesystems. Request bytes may contain sensitive data; restrict directory access.

`open` acquires an exclusive process lock. `reserve` creates an irreversible single reservation containing scope, machine identity, request ID, and exact request bytes, and forces the file and directory. Its caller must keep the lock throughout any future dispatch and reconciliation. Errors, partial records, and existing reservations block a new reservation. After a crash or unknown outcome, do not resend; an operation lookup returning NOT_FOUND does not prove the effect was absent. `inspect` only reads an existing structurally valid record after matching the supplied scope and identity. It neither verifies those values against a machine nor detects every structurally valid corruption.

Recovery requires stopping all participants, preserving evidence, independently establishing remote state and machine identity, and a documented human decision before creating a new domain. Do not replace the lock or reservation while participants may be active. The API does not enforce this procedure. Correctness also depends on the operating system and filesystem honoring exclusive locks, create-new, and file and directory force; host tests do not prove power-loss durability.

The Java host tests exercise restart, process contention and death, byte truncation, invalid encoding, identity mismatch, and immutable reservation. The lookup tests exercise mismatched requests, scopes and labels, corrupt reservations, and a timed-out lookup without enabling mutation dispatch. They do not test integrated mutation dispatch, remote reconciliation, VM behavior, or power loss. A reservation does not prove dispatch or completion.

`State.RESPONSE` validates only the outer lookup envelope. `assessReservedLookup` rejects inconsistent or malformed available identifiers and returns `UNVERIFIED` for pending, unknown, terminal, errors and timeouts; it does not validate a terminal receipt or establish machine identity or a visible effect. No result authorizes replay.
