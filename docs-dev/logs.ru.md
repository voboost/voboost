# Логи

[English](logs.md) | **Русский**

Voboost использует один постоянный диагностический поток. Только voboost-daemon пишет общие логи в /data/voboost/logs. Inject проверяет источники сообщений приложения и агентов и передаёт записи через закрытый протокол владельцу; сами файлы логов он не записывает.

## Уровни

Допустимы ровно три уровня:

- `debug` — проверки, ветви решений, повторы и пропущенные действия
- `info` — успешные изменения состояния и завершённые этапы
- `error` — действие не выполнено, завершилось ошибкой или требует восстановления

Уровня `warning` нет. Производитель записи обязан выбрать один из трёх уровней до отправки.

## Источники

Демон выводит `source` из проверенного транспорта, а не принимает его как доверенное поле производителя:

| Источник | Транспорт | Как определяется |
| --- | --- | --- |
| `daemon` | внутренняя очередь процесса | компонент известен внутри демона |
| `agent` | канал среды конкретного процесса | соединение связано с PID, временем запуска, поколением и ID агента |
| `app` | отдельный сокет `ru.voboost` | учётные данные второй стороны и процесс пакета связываются с приложением |
| `qnx` | канал сопряжения Android и QNX | подтверждённая сторона соединения и её сеанс связывают записи с приборкой |

Агент не может написать сообщение от имени другого агента, приложения или демона. `ru.voboost` не может передать произвольный `source`. Демон принимает app-соединения последовательно, но каждое чтение и ответ ограничены двумя секундами: оборванный после connect или посреди пакета процесс не может навсегда заблокировать следующие пакеты.

## Формат записи

После приёма демон создаёт каноническую запись:

```json
{
    "schemaVersion": 2,
    "bootId": "11111111-1111-4111-8111-111111111111",
    "writerId": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "sequence": 1042,
    "timestamp": "2026-09-01T08:15:30.123Z",
    "source": {
        "kind": "agent",
        "id": "vehicle-drive-forced-ev"
    },
    "level": "debug",
    "component": "contract",
    "message": "provider read matched",
    "fields": {
        "predicate": "forced-ev-state",
        "result": "MATCH"
    }
}
```

`sequence` растёт внутри одного сеанса writer. Идентичность записи — `(writerId, sequence)`; `bootId` связывает её с загрузкой Android. Перезапуск демона создаёт новый writer ID и начинает последовательность заново. `timestamp` обозначает время приёма и не задаёт порядок событий. `source.id` обязателен для подтверждённого агента.

Записи установщика и резервного stderr используют локальные последовательности производителей. Пакеты QNX содержат сеанс источника и номер последовательности. Демон Android присваивает полученным записям канонический идентификатор. Их номера не задают порядок между процессами и сеансами writer. CLI установщика пишет диагностику JSONL в stderr, оставляя stdout результатам команд и протоколам. `VOBOOST_LOG=debug` включает подробности транспорта; по умолчанию действует порог `info`.

Владельцы с диагностикой по изменениям записывают ожидание на уровне `debug` при изменении диагностического контекста. Подавление повторов влияет только на вывод: проверки, повторы действий и публикация состояния продолжаются. Смена идентичности, причины или lifecycle открывает новый эпизод. Независимые ошибки сохраняют отдельные записи `error`.

Одна запись не превышает 16 КиБ после канонизации. Число полей, длины ключей и строк имеют закрытые пределы. Неизвестные поля, управляющие символы, неверный UTF-8 и значение уровня вне закрытого списка отклоняются.

## Логи приложения до запуска демона

`ru.voboost` может запуститься раньше демона, поэтому хранит только неподтверждённую очередь в:

```text
/data/user/0/ru.voboost/logs
```

Это не второй постоянный лог и не отдельная точка чтения. Приложение кратковременно группирует записи в памяти, после чего атомарно создаёт файл `batch-<128‑bit-id>.json` с `fsync`.

Пакет закрывается при первом условии:

- добавлена запись `error`
- прошло 250 мс с первой записи
- накоплено 64 записи
- канонический размер достиг 256 КиБ

Приложение отправляет пакет демону и не более трёх секунд ждёт ACK с тем же 128‑битным ID. Демон сначала сохраняет записи и надёжно фиксирует принятый ID, затем возвращает ACK. После ACK приложение удаляет файл. Истечение времени ожидания или разрыв соединения сохраняют тот же пакет для повтора, а повтор уже принятого ID возвращает тот же ACK и не создаёт дубли.

Перечисление, чтение, сокращение и удаление очереди выполняются относительно удерживаемого дескриптора каталога. Принимаются только принадлежащие приложению обычные файлы `0600` с одной ссылкой. Символическая или жёсткая ссылка и смена inode отклоняются без чтения и удаления цели.

Каталог приложения ограничен 2 МиБ. При переполнении сначала удаляются самые старые `debug`, затем `info`. Если остаются только `error`, удаляется самая старая запись и создаётся один `error` о потере сообщений. Новая запись о переполнении не должна рекурсивно создавать новые записи.

## Хранение демона

Общий лог состоит из трёх независимых потоков по 128 МиБ каждый: канонический поток всех уровней (`all/debug`), совместный поток `info`+`error` и поток только `error`. В каждом потоке не более шестнадцати завершённых или активных JSONL-сегментов по 8 МиБ, поэтому суммарный худший случай трёх потоков — 384 МиБ. Демон пишет только в активный сегмент каждого потока, выполняет `fsync` с ограниченной задержкой и закрывает сегмент перед ротацией.

При достижении лимита удаляется самый старый завершённый сегмент. Активный сегмент или файл с неверным владельцем, правами, типом или числом ссылок не удаляется как обычная ротация; логирование переходит в ограниченное состояние ошибки, не останавливая агентов.

После ошибки записи или синхронизации демон закрывает файлы этого writer. Следующая запись повторяет восстановление с задержкой от 250 мс до пяти секунд. Восстановление создаёт новый writer ID и начинает последовательность с единицы; демон не дописывает потенциально оборванный старый хвост. Восстановление могут запустить записи демона, пакеты приложения и QNX. При повторе существующих неизменяемых пакетов сохраняются исходные идентификаторы записей.

Логи не входят в `state/`, `operation.json` или журнал системной операции. Переполнение или повреждение логов не блокирует запуск агента, установку, обновление или восстановление.

## Запросы логов

Владелец хранилища не предоставляет live query/follow. Используйте ограниченную выгрузку. Читатель должен связывать курсор с подтверждённым сеансом writer, а не считать номер последовательности глобальным.

## Выгрузка через voboost-installer

Для установленного продукта действие **Скачать логи** доступно на экране управления; для неизвестной установки — на диагностическом экране. Системный выбор папки выполняет Rust backend. CLI использует команду:

```text
voboost-installer --logs <каталог>
```

CLI и GUI используют один механизм чтения доверенных файлов по фиксированным путям. Он читает существующие файлы Voboost через ADB, в том числе сохранённые сегменты в `/data/voboost/logs` и доступные данные о ходе установки. Сбор работает даже при отсутствии исполняемого файла демона. Установщик ограничивает объём и проверяет данные на компьютере, в том числе полноту записей JSONL и их идентификаторы. Для закрытых источников нужен shell с правами root. Установщик проверяет метаданные файлов и оставляет неподтверждённые пакеты в закрытом каталоге приложения.

Сборщик получает доступную пассивную диагностику Android до запроса `adb root`, если он нужен. Сборщик привязывает запрос root и переподключение к выбранному устройству, проверяет UID полученного shell и повторяет незавершённые чтения с ограниченным ожиданием. Наблюдения разных загрузок Android различаются по ID загрузки. Отсутствие файла, пустой файл и ошибка чтения дают разные результаты.

Установщик записывает один архив на компьютере.

```text
voboost-logs-<дата-UTC>-<время-UTC>-<32-hex-случайный-токен>.tar.xz
├── manifest.json
├── records.jsonl
└── context.json
```

Метка времени имеет вид `YYYY-MM-DD-HHMMSS`. Манифест сохраняет `schemaVersion: 1` и `format: "VBOOSTLOG1"`. Он содержит размеры двух файлов с данными и связывает архив с выбранным устройством, если оно известно. В `context.diagnosticBundle.sources` указаны результаты, причины, время, ID загрузки и объём по каждому источнику. Установщик включает в архив текущую сессию. На машине он не создаёт архив или временный каталог и не захватывает `operation.lock`.

Если сборщик получил часть данных машины и один из источников дал ошибку, сборщик сохраняет доступное и сообщает `partial`. Если получить пригодные данные машины не удалось, сборщик сообщает `failed` и сохраняет журнал установщика внутри архива. В этом случае установщик также пытается записать отдельный локальный журнал. В обоих случаях код завершения CLI ненулевой. GUI показывает результат сбора и путь к архиву. Подтверждённое отсутствие файлов Voboost на чистой системе считается ожидаемым результатом источника.

## События приборки

Только `voboost-daemon` на Android записывает постоянный журнал событий Voboost, включая записи с источником `qnx`. QNX держит события в ограниченной очереди в оперативной памяти и передаёт их по каналу сопряжения. Демон подтверждает пакет после записи. Если подтверждение потерялось, при повторе используются те же сеанс источника и номер последовательности, чтобы избежать дублей. При переполнении очереди или потере питания приборки ещё не переданные события могут пропасть.

Внутри одного процесса демона QNX повтор возвращает те же байты пакета до точного подтверждения. Извлечённые ячейки остаются занятыми в общей RAM до этого подтверждения. После перезапуска процесса неподтверждённые ячейки становятся отметками потерь и входят в `dropped` следующего сеанса источника; эти отметки и счётчик переполнения остаются в RAM до подтверждения. В этот счётчик может попасть пакет, уже сохранённый на Android, если QNX не завершила обработку подтверждения. Это явный учёт отброшенных неподтверждённых событий, а не гарантия однократной доставки между перезапусками процесса. Перезагрузка QNX или потеря питания очищает RAM. Файловые логи на QNX не создаются.

Сборщик читает эти события с Android и сохраняет доступное состояние доставки. Он отличает подключённую приборку без полученных записей от недоступной доставки и профиля без поддерживаемой приборки.

`qnx-delivery.json` сохраняет надёжно записанную позицию источника, закрытую категорию `failureCategory` (`configuration`, `transport`, `timeout`, `protocol` или `storage`) при недоступной доставке и `lastSuccessAt`, если уже был успешный опрос. Категория не содержит текста от второй стороны или учётных данных. Повторный отказ той же категории не перезаписывает файл и не создаёт повторных сообщений ожидания. Успешный опрос снимает категорию отказа; время успеха хранится в памяти при подключении и записывается при смене состояния или сохранении пакета. После аварийного завершения Android-демона в файле может остаться более раннее время, чем у последних успешных опросов без новых записей.

## Конфиденциальность

В лог не записываются:

- закрытые и одноразовые ключи
- токены авторизации
- полные заголовки HTTP
- содержимое пользовательских файлов
- VIN и идентификаторы учётной записи
- произвольные снимки памяти

Перед сохранением демон скрывает известные формы токенов и ограничивает каждое поле. Архив принадлежит пользователю и никуда не отправляется автоматически.

## Удаление

Удаление стирает очередь приложения, общий лог, завершённые подписки и все временные файлы выгрузки. Архив, ранее сохранённый на компьютере, не принадлежит машине и автоматически не удаляется.

## Источники реализации

- `voboost-app/src` — очередь приложения, схема пакета и клиент ACK
- `voboost-agents/src` — диагностика stable-агентов
- `voboost-inject/daemon` — однозначные записи, хранение, запросы и выгрузка
- `voboost-installer/src-tauri/src/diagnostic_collection.rs` и `diagnostic-read.sh` — общий сбор через ADB и результаты выгрузки
- OpenSpec `app-logging`, `runtime-observability`, `agent-logs` и `operation-adb-execution`

## Обязательные проверки

- подмена источника и несовпадение второй стороны
- повтор ID пакета без повторных записей
- предел 64 записей, 256 КиБ и 250 мс
- переполнение очереди приложения и одна нерекурсивная запись о потере
- ротация сегментов и некорректные объекты файловой системы
- пределы запросов, фильтры, курсоры, устаревший запрос и остановка
- отсутствие уровня `warning`
- ограниченные чтения по ADB, фиксированные пути и проверка метаданных файлов
- сохранение пассивных данных при сбое root или разрыве USB
- частичный результат и ошибка CLI, общий результат GUI
- повтор пакетов QNX, удаление дублей и потеря ожидающих событий
- контекст при недоступном демоне
- отсутствие закрытых пакетов приложения в выгрузке
- отсутствие следов выгрузки на машине

Тесты на компьютере не доказывают интерфейс настроек машины, реальный SELinux или диагностику физического устройства. Это проверяется отдельно на эмуляторе и устройстве.
